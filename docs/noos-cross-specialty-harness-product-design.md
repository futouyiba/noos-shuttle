## 1. 如何继续这份设计（本对话工作记忆）

用户约定原文：

> “我一边讨论，你一边把一些点就往设计文档里面去改。然后改着改着达到了一个相对稳定的程度就形成提交，防止聊着聊着把前面的东西又忘了。”

后续本任务按以下方式持续推进：

1. 每轮聚焦一个问题，先读本文相关共识与未决项，再讨论；不要求用户重述整个项目。
2. 当轮形成的共识、理由、未决问题及变更原因及时更新本文，不为每轮讨论另建 amendment。
3. 明确区分用户已确认方向、助手建议、开放问题与既有契约；用户批准讨论计划不等于接受全部候选方案。
4. 已确认内容发生变化时，记录新依据与取代关系；不悄悄删除此前的关键取舍理由。
5. 一组设计相对稳定后做本地阶段提交。本次计划授权阶段性提交，不授权自动 push、建远端 PR、merge、部署或关单。
6. 稳定方案按仓库流程接受独立评审；触及契约时另行提交裁定。检查点提交不等于评审 APPROVE。
7. 本文是跨会话可恢复的工作记忆，不声称聊天平台已保存永久 memory；原对话保留为来源，不整段复制为主要设计输入。

恢复入口：第一阶段已落盘；下一轮从 §5 场景 A 的实际换对话经历开始。首版优先级尚未确定。

## 2. 已确认的产品方向

### 2.1 两个出发点

- 用户希望保留 ChatGPT 网页版作为深度思考、产品讨论的场所，通过外部支撑补足工作连续性与行动循环，而不是为了执行能力被迫迁往另一种讨论体验。
- 用户希望减少 Chatbot、Coding Agent、视觉创作工具之间反复搬运材料、解释背景、转送结果的负担。

上述 ChatGPT 偏好来自用户的使用体验，不是跨产品能力评测结论，也不以某个平台永久缺少某项功能为产品前提。

### 2.2 产品定位与命名

用户对职责归属的原文：

> “Coding 内部的 Harness 他们自己管。”

> “Design 内部的 Harness 由于发生在 ChatGPT 这种 chatbot 里面，我们就来接管。”

> “或者准确地来说，是 Noos Hub 来接管。Noos Shuttle 是浏览器当中跟 Chatbot 和画图工具桥接的一个桥梁，一个交互界面。”

据此沉淀的产品方向：**NOOS Hub 是跨专业工作过程的 Harness 中枢；NOOS Shuttle 是浏览器侧的桥梁与交互界面。**

Hub 的目标覆盖深度调研与讨论、产品设计、视觉创作、代码实现、原型验证之间的工作循环；不是要求某一个模型或工具承担全部过程，也不是把所有工具已有的内部执行机制重做一遍。

| 领域 | 已确认方向 | 尚未确定的深度 |
| --- | --- | --- |
| Coding 内部 | Coding Agent 自管内部 Harness | Hub 与其交互的最小任务、状态和结果接口 |
| Design 内部 | Hub 为 Chatbot 补足工作连续性及外部行动能力 | 自动沉淀、换会话、委派与恢复各自的权限和触发方式 |
| 视觉创作内部 | 纳入整体产品方向，倾向由 Hub 补足 | 接管范围、工具能力、素材与版本交互，后续专项设计 |
| 跨专业协作 | Hub 管理各专业之间的协作循环 | 分工建立、并行依赖、结果接纳和人工决定点 |
| 浏览器交互 | Shuttle 连接 Chatbot 与视觉工具 | 具体操作能力依平台验证，不预设万能适配器 |

ChatGPT 是重点入口，不是永久唯一的工作中心。专业角色可以持续负责各自领域，用户的工作不绑定单一工具。

### 2.3 团队式协作与上下文隔离

用户原文：

> “搞设计的，就专门搞设计，搞开发的就专门搞开发，让他们的上下文维持相对隔离”

设计取向是专业化协作：角色通过任务、决定、证据和结果连接，不默认共享所有聊天历史。理由是减少无关材料、过时意见与不同角色目标互相干扰；不把这一动机当作未经验证的模型性能定律。

隔离不等于不能追问或查阅来源。具体共享范围、补充上下文的方式及成本，留待第三阶段确定。

### 2.4 三种用途不混用

| 用途 | 要保留或传递的连续性 | 不应被等同为 |
| --- | --- | --- |
| 同角色跨会话续接 | 先沉淀，再到新对话继续同一角色的工作，产生类似 compact 的效果 | 将全部旧对话重新灌入，或自动转交另一角色 |
| 跨角色交接 | 保持分工，交付对方需要的任务、依据、约束和结果 | 将发送方的全部工作记忆复制给接收方 |
| 知识沉淀 | 保存可复用结论供未来工作使用 | 默认启动任务、切换会话或授予执行权限 |

既有 Crystal 可提供续接所需的部分材料，但是否足以承载角色工作记忆需要验证，本文不改变其既有定义。

## 5. 后续讨论与阶段检查点

### 第二阶段：真实场景与优先级

按以下顺序讨论，但不据此预定实现顺序：

| 场景 | 已知用户动机 | 下一轮要补齐的事实 |
| --- | --- | --- |
| A：设计讨论换新对话继续 | 先沉淀，再迁移，实现类似 compact 的工作记忆续接 | 最近一次实际换对话的原因、携带材料、丢失内容与重述成本 |
| B：设计向开发或视觉角色交付并接回结果 | 专业上下文相对隔离，避免人工搬运 | 一次真实交付的输入、完成标准、追问过程及接收结果方式 |
| C：调研到原型验证再返回设计 | 打通不同工具不能单独覆盖的全过程 | 选择一项实际产品工作，识别迭代、并行、返工和人工决定点 |

每个场景补齐：用户目标、角色分工、必要上下文、交付物、人工决定点、完成标准、失败恢复方式。用用户确认的实例记录旅程，不代填为已验证事实。

退出条件：三个场景已讨论并得到用户确认；首版必需能力、优先级与后续扩展明确。届时形成第二笔设计提交。

### 第三阶段：工作记忆与协作规则

基于场景划分团队共同依据、角色记忆和历史材料，确定续接与交接各自携带的信息；明确决定、候选、否决及未决状态，以及结果接纳、依据变化和中断恢复的责任。

优先对照既有 Work Item、Logical Thread、Handoff、Crystal、Result、Context Pack；对象对应关系是待验证设计，不以名称相近直接视为等价。只有场景证明有缺口时，才提出新接口、类型或对象。

退出条件：职责与信息流明确；既有设计对应表及需要裁定的差异齐备。届时形成第三笔设计提交；涉及契约的差异另走裁定，不在本文直接生效。

### 第四阶段：交互与首个产品切片

围绕第二阶段选定的最高优先级场景，设计入口、用户可见状态、交接确认、失败恢复和人工控制；不提前规定页面或按钮结构。

桌面推演必须覆盖：

- 新对话能否继续同一角色工作，无需用户重讲整个项目。
- 接收方材料是否足够，且未默认灌入无关历史。
- 旧建议是否可能误升格为已确认决定。
- 返回结果能否对应原任务，而不自动等于接纳或继续执行。
- 材料缺失、投递失败、会话失效时，材料是否保留、责任是否清楚、下一步是否可见。

退出条件：体验方案、验收场景、首个切片与非目标明确，并记录推演暴露的问题。届时形成第四笔设计提交，之后才讨论实现授权。
