## 1. 产品定位（已确认）

**NOOS Hub 是跨专业工作过程的 Harness 中枢；NOOS Shuttle 是连接浏览器工具的桥梁与交互界面。**

服务于深度调研与讨论、产品设计、视觉创作、代码实现和原型验证之间的持续工作。核心价值是补足单一工具的工作循环，并减少工具之间反复搬运材料、重述背景和转送结果的负担。

ChatGPT 网页版是用户偏好的深度讨论入口，不是永久唯一的工作中心。该偏好不是模型能力评测，也不以某个平台永久缺少某项功能为前提。

| 层次 | 职责方向 | 保留边界 |
| --- | --- | --- |
| Coding 内部 | Coding Agent 自管内部 Harness | Hub 不重新管理代码探索、编辑和测试细节 |
| Design 内部 | Hub 为 Chatbot 补足工作连续性与外部行动循环 | 自动沉淀、委派、续接的具体机制待定 |
| 视觉创作内部 | 纳入产品方向，倾向由 Hub 补足 | 接管深度、素材与版本交互后续专项设计 |
| 跨专业协作 | Hub 管任务交付、返回与协作连续性 | 不因“中枢”定位自动取得语义裁决权 |
| 浏览器侧 | Shuttle 负责连接与交互 | 实际操作能力按平台验证，不预设万能适配器 |

专业角色保持上下文相对隔离，通过任务、决定、证据与结果协作；不默认共享全部聊天历史，也不阻止必要的追问与来源查阅。

用户的实际设计习惯是按主题分别开对话，例如整体设计、子系统设计、模块设计与某个设计问题的拆分聚合；对话之间通过文档互通信息。这不是按每轮开发重新配置负责人。主题可以有粗细之分，但名称上的层次不自动构成审批或指挥关系。确认来源见[决策记录 D6](noos-cross-specialty-harness-decision-record.md#d6--按主题组织设计对话用户使用事实)。

## 2. 核心使用场景（方向已确认）

| 场景 | 目标 | 与其他场景的区别 |
| --- | --- | --- |
| 同角色续接 | 先沉淀工作记忆，再到新对话继续同一角色的工作 | 不是全量重放历史，也不是交给另一角色 |
| 跨角色交接 | 交付有边界的任务、依据、约束，接回结果 | 不是复制发送方的全部记忆 |
| 知识沉淀 | 保存可复用结论供未来工作使用 | 不默认启动任务、切换会话或授予权限 |

工作记忆与未完成协作事项不能混为一份摘要：设计角色换会话后，仍需知道哪些请求待处理、谁在等待、结果返回哪里。具体承载方式待定。

## 3. 场景 B1：开发请求设计回应

用户已要求优先收敛裁决整体流程并交给 CC 开发；专项交付见[裁决自动往返 MVP](deliberation-harness/adjudication-roundtrip-mvp.md)。该方案区分当前实现证据、待开发连接与恢复门禁；本节仍是产品体验候选，不修改 #63 已生效的 outbox 裁定。

### 3.1 已确认的体验要求

- 消除用户在开发与设计之间来回传话的负担，不只是把复制长文变成反复提醒“去看看”。
- 预先指定角色及授权范围后，请求可自动触发设计方思考、答复，不逐次等待点击；超出授权的决定再交给用户。
- 设计角色忙碌时排队，不默认强行中断；何时接续的具体规则仍在收敛。
- 不默认另开一个缺少设计背景的临时设计师绕过等待。

用户最新建议先补齐人工输入的排队体验，让人与其他 Agent 的请求可以先后处理，而不要求保护整段讨论期间不出现外部请求。§3.4 据此改为按请求接续的候选；具体顺序与输入入口尚未确认。页面失焦、沉默或生成结束都不产生新的授权。

### 3.2 候选协作流程

原 Agent 准备并持久提交有界问题与依据 → Hub 关联原任务并路由 → 指定设计方处理或追问 → 补充材料与答复沿原任务自动往返 → 开发按现有授权与门禁决定后续动作。

#### 3.2.1 请求怎样进入主题

开发侧只需知道这项工作的设计问题交给哪位已指定的主题负责人，不承担找窗口、选择会话版本或人工回传的责任。负责人可跨多轮开发持续工作；每个请求仍独立关联原任务、问题与适用依据。主题责任不固定在某个窗口，也不按每条消息重新建立委派；不能仅凭主题名称推定裁决权限。

多数代码阅读、验证与材料准备仍由原 Coding Agent 完成；不默认每个请求再启动一个助手。准备不能变成“材料完美后才允许提问”的无限门槛。

请求在待发区用一条简短摘要呈现，进入处理时保留可辨认的来源。展开才阅读所需依据，不默认把整段开发聊天送入主题：

| 阅读层次 | 内容 | 由谁准备 |
| --- | --- | --- |
| 列表摘要 | 来自哪个角色与任务、一个具体问题、在等待谁 | 从已有任务关联与提问中形成，不让用户重复填表 |
| 本次处理材料 | 必要背景、问题、已确认依据及版本、关键证据、希望得到什么答复与不做什么 | 原 Agent 组织；Hub 按已有身份及授权投递 |
| 按需追读 | 完整相关文档、原始证据及更多实现细节 | 保留可访问来源；确需更多材料时再请求补充 |

这是一份已有 Handoff / Context Pack 的用户可读呈现，不新增“问题卡”权威对象。摘要不能替代适用依据，来源标签不能自证权限。目标读不到仓库或本地引用时，需在允许外发的范围内提供相关原文及版本来源；不能只投一个不可访问的链接，也不能因此上传全部历史。

以下仅为用户主题的情境示例，不包含该业务的已批准设计决定：开发围绕“饵和姿态的吸引因子拆分与聚合”提出一个边界问题，请求说明允许范围和理由，而不是要求设计对话直接改代码。请求依 §3.4 进入现有主题队列；用户可以查看，但无需替开发敲一条“请看这个问题”。

#### 3.2.2 回应怎样返回原任务

设计回应需要交代适用问题与依据、决定及理由、允许与不允许的范围。无法决定时明确缺什么或需交谁处理；设计方不默认接管 patch。

| 回应情况 | 候选交互 | 用户承担什么 |
| --- | --- | --- |
| 依据充分且已有对应授权 | 设计支持答复直接回到原 Coding 任务，不必额外绕主设计方重复批准；是否可应用仍按现有门禁 | 不负责中继；可查看决定与依据 |
| 缺少实现事实或证据 | 带具体缺口向原 Agent 追问，补充回到同一问题；不可把追问记录为已解决 | 通常无需介入；事实只能由用户提供时才询问用户 |
| 需要改变未被委派的设计决定 | 将已知依据、冲突、选项与待决点交回指定主设计方；只有属于人类保留权限才进一步交给用户 | 参与真正需要自己的决定，而不是转发全文 |

以上是用户可见的回应方式，不新增协议 outcome 枚举。若缺少安全投递能力或权限范围不明确，显示阻塞而不是把问题强行归入可自动答复类。重复追问仍不能收敛时，应呈现具体缺口请求介入，不做无限来回对话。

自动回传只针对已经关联的外部请求，不把用户的普通聊天回应一律发送给 Coding Agent。以该次操作及可信结果边界取得可核对的完整答复，保留来源和适用依据；不能抓取页面上最后一段文本，或由 Hub 擅自重写为新的语义裁决。捕获、格式整理和投递的具体平台机制尚需验证，生成停止或文本中出现“完成”并不足以证明结果可回传。

返回路径在请求建立时关联，不在答复后再让用户选择收件人。权限及通道已具备时，答复或追问直接沿原任务返回；追问所需补充仍归同一个问题，不建立第二个无关联任务。补充造成问题或适用依据变化时，复用既有修订关系，不原地改写已投递材料。

用户侧以同一请求的回执区分“答复已生成”“回传待核实”和“已回传”；只有确认投递结果后才显示后者。请求等补充时说明等哪个角色，只有确需用户裁定时才提示用户作决定。投递失败保留已产生答复并恢复原投递，不默认让设计方重想一遍；必要时查看原文，而非只留一个成功图标。这些是现有事实的界面投影，不是第二套状态机。

投递、接收、产生答复、授权接纳与恢复执行是不同事实。设计方追问不等于已解决，收到结果不等于自动批准继续、合并或部署。

### 3.3 候选异常体验

- 引用不可读：明确材料缺口，不擅自上传完整私有历史。
- 发送结果不确定：核实后重试，不重复创建逻辑任务。
- 会话更换：继续关联负责角色和原任务，不依赖过期窗口地址。
- 目标不可用或无法安全触发：保留待办并显示原因，不声称正在处理。
- 等待过久：聚合提示；等待时长不能扩大权限或替代裁决。
- 正式依据变化：在途结果保留原依据，接纳时不得静默沿用或自动合并。

### 3.4 人与自动请求共用主题对话（候选）

**先补齐输入排队，而不是判断用户是否结束讨论。** 以用户描述的 Agent 使用习惯为参照：负责人处理当前输入时，用户仍能编辑并提交下一条；其他 Agent 的有界请求也能进入待处理序列。当前回应结束后再接下一条，不要求用户离开主题。此处是 NOOS 的候选体验，不是对任何平台现有能力的断言。

Hub 接收并关联输入，Shuttle 提供生成期间仍可使用的编辑与排队体验。用户草稿与自动投递内容分开保存；发给模型的请求不能借用或覆盖用户正在写的草稿。用户侧维持一个主要输入入口，具体候选见 §3.5；增强原输入框还是在原位置提供托管输入区，留待平台验证，不让用户日常在两个入口之间判断。

候选默认是同一主题按接单顺序、一次处理一项输入及其对应回应，不是一次占用整个主题或开发任务。未提交的草稿不占队列位置；人类输入不因来源而自动抢占，紧急纠正或中断需要明确操作。只把目标、权限与材料满足条件的请求交给对话；等待外部补充的事项保留关联，不占着当前处理位置阻塞后续输入。

| 情况 | 候选处理 | 用户可见结果 |
| --- | --- | --- |
| 正在回应用户，收到开发问题 | 开发问题排队，不中断本条回应 | 看得到请求来源、摘要及等待位置 |
| 正在回应开发问题，用户提交新输入 | 用户输入进入同一序列，不要求等生成结束才能发送 | 明确显示“已排队”，而非误称已经发给模型 |
| 当前回应结束且下一条具备处理条件 | 关联本条结果，依序提交下一条；不检查用户是否离开 | 用户留在页面也能自动接续 |
| 用户修改或撤回自己的待发输入 | 仅操作尚未提交到平台的条目；候选采用撤回到草稿、重新发送后重新排队 | 草稿不被覆盖，已发出的不能假装撤销 |
| 用户需要立即纠正当前工作 | 单独提供明确的中断路径，能力按平台验证；不把普通发送解释成中断 | 中断与排队有可辨认的区别 |
| 提交或生成状态不确定，或出现绕过托管入口的输入 | 暂停自动续发，核实实际消息与操作关联，不盲重发 | 保留待办并说明阻塞，不错配返回结果 |

示例：用户问题 A 正在处理 → 开发请求 B 排队 → 用户补充 C 排队 → A 完整结束后处理 B → B 完整结束后处理 C。用户能提前表达 C，但默认接受 B 先处理；如果 C 是要求立即停止当前工作，应走明确中断，而不是依靠系统猜测文字的紧急性。

用户需要看见“正在回应谁、还有哪些输入待处理”，不需要维护忙闲开关。每项输入保留真实来源和原任务关联；Agent 请求即使经网页输入框提交，也不等于用户指令或新的授权。回应按实际处理的请求返回，不能把屏幕上的最新文本一律交给 Coding Agent；部分生成、人工中断和归属不明的文本不视为完整答复。

请求仍携带适用的已确认依据；当前讨论中的候选想法不因共用对话变成新决定。依据变化、权限撤回或任务已失效时，相关待发请求须重新核对，不能因排到了就照常执行。完整回应、结果接纳和恢复开发仍是不同事实。

该方案解决输入争用和等待时不能提交的问题，不消除排队延迟、话题交错或上下文负担。第一轮只验证可编辑、可排队、依序处理、来源可辨与结果不串线，不预设优先级算法或复杂 Governor。可靠性限于实际受控并经验证的输入入口；不能声称覆盖所有设备或原生绕行输入。队列须复用既有身份、投递与控制语义，不新增平行状态机，也不绕过既有 automatic-resume gate。

输入排队与上下文保护是两个主题。用户提出可以显式锁住某个对话，避免外部请求增加其上下文；这不是恢复人人日常维护忙闲开关的默认要求。“何时允许进入主对话”与“由原对话还是其他承载回应”分别登记为 Q11 / Q12，本轮不展开。离开后处理可作为后续策略候选，fork 也只是回应来源的候选；不因提出这些可能性而认定已获功能或执行授权。

### 3.5 排队输入的最小界面（候选）

本节将 B1 的输入排队细化为桌面推演稿，不代表完整首版切片已经选定，也不构成 UI 实现授权。文案仅用于说明候选交互。

#### 3.5.1 同一对话中的三个部分

建议在现有对话底部的熟悉位置提供以下界面，不另开工作台，不复制整份聊天：

| 部分 | 展示内容 | 操作 |
| --- | --- | --- |
| 当前处理条 | “正在回应：你 / 开发 · 问题摘要”；空闲、已停止或待核实时如实显示 | 查看对应输入；支持时可停止本次回应 |
| 待发摘要 | “待发 2 条”，展开才显示来源、短摘要与顺序 | 查看正文；自己的未发条目可撤回到草稿 |
| 主输入区 | 当前主题、用户草稿、可选的回复引用；始终可以编辑 | 主按钮始终为“发送”；有前序工作时旁注“将依序发送” |

普通发送始终提交到同一接续流程：无前序工作且条件满足时立即投递，否则显示“已排队”。只有接收方确认保存后才把内容从输入区移入待发列表；尚未确认时保留草稿并显示状态，不用清空输入框冒充接收成功。排队内容不提前伪装成平台已经收到的聊天消息。

Agent 请求直接进入关联主题的待办，不经过用户草稿。Hub 承载接收与请求关联，Shuttle 展示和投递；不为每条人工输入创建 GitHub 评论，也不向 GitHub 复制完整队列。

#### 3.5.2 最小操作规则

- **普通发送**：依 §3.4 接续，不自动插队或改成对当前生成的干预；用户无需选择“人工 / Agent 模式”。
- **撤回到草稿**：仅限自己的未发条目；撤回成功才从待发列表移除。重新发送排到队尾，不承诺保留原位置。已有新草稿时先保留两份内容供选择，不覆盖或自动拼接；若恰好已提交到平台，则明确提示不能撤回，可另发补充。
- **停止本次回应**：是与发送分开的明确动作。先停止后续自动投递，再核实本次生成是否已停止；待发内容保留，不能停止 A 后马上自动开始 B。用户明确选择“继续处理待发”才恢复。这是一次中断后的恢复，不是日常忙闲开关；平台不能可靠停止时不得显示“已停止”。
- **继续处理待发**：按原序重新核对目标、权限和依据。中断前的半截输出不作为完整答复；本轮不做拖拽排序、自动提权或“停止并插队”的组合操作。
- **回复引用**：可点选回复某条输入或回应，排队期间保留该关联，不被随后到来的 Agent 消息替换。不要求每条都加引用；未明确指向的“这个方案”仍可能需要澄清，不能声称排队解决了所有语义歧义。

#### 3.5.3 三条输入的桌面推演

设 A 是用户的主题设计问题，B 是开发的有界请求，C 是用户对 A 的补充；表中只推演候选规则，未执行真实平台验证。

| 时刻 | 用户看到什么 | 要验证什么 |
| --- | --- | --- |
| A 正在回应，B 到达 | 当前条仍是 A，待发显示开发问题 B | 不中断 A；B 不被误标为用户指令 |
| 用户编辑并发送 C | 输入区可用；接收成功后队列显示 B、C | 无需等待 A 结束才能提交；草稿未被 B 覆盖 |
| A 结束，开始 B | 当前条切换为开发问题 B；C 仍显示待发 | 用户留在页面也能接续；C 的已有回复引用不改指 B |
| B 结束，开始 C | B 的结果关联原开发任务；当前条切换为用户补充 C | C 的回应不能被当成 B 的结果回传 |
| 用户在 B 期间停止 | 显示停止中的真实状态；C 留在待发区 | 部分 B 不作完整答复，C 不偷偷启动 |
| 刷新、重连或发送状态不明 | 恢复已保存的草稿和待发项；状态不明者先核实 | 不因缺少即时回执重复投递，不宣称尚未确认的操作成功 |

先用一个主题、文本输入、用户与一个 Coding 来源检验这一段体验；附件、多平台并发和优先级调度不在本轮推演中定案。成功标准是能提前表达、看懂顺序、取回未发内容，且答复不串线。实际平台接入、持久化和契约映射的可行性仍需后续验证。

## 4. 候选职责与工作组织

本节均待用户确认；不新增当前契约之外的运行权限。

### 4.1 GitHub、Hub 与 Shuttle

| 承载方 | 适合负责 | 不应承担 |
| --- | --- | --- |
| GitHub | 仓库相关的有界问题、正式答复、review、验收证据和重要补充材料的共享记录 | 所有私有上下文、细粒度运行状态，或仅凭评论/标签授权执行 |
| Hub / Vault | 任务关联、角色路由、投递与恢复、工作记忆、选择性材料投递、产物来源与存储引用 | 替专业角色作语义裁决，或维护与已有 reducer 冲突的控制面 |
| Shuttle | 网页输入、附件投递、状态观察、结果捕获及交互反馈 | 独立任务真源、设计批准或恢复执行的裁决 |

GitHub 可作为仓库协作的共享后端，但不成为纯设计、视觉工作或同角色续接的强制依赖。完整聊天、访谈和探索草稿默认本地保存；图片与工程文件由 Hub 管理引用和来源，实体存储依工具另定。

每类事实有明确责任方，不做无差别双向全量同步。GitHub 是共享来源，Hub 保存不可变观察与投递关联；正式权威仍来自指定契约和授权角色，不来自存储位置。外发材料需匹配授权范围。

### 4.2 工作会话的用途

按交付物分类，不是五个常驻职位或新增协议枚举。

| 用途 | 典型交付 | 边界 |
| --- | --- | --- |
| 调研取证 | 带来源的发现、反例、信息缺口 | 区分事实与推断；不擅自联系用户或外发资料 |
| 专项设计与创作 | 方案、草图、理由，或授权范围内的设计回应 | 默认提供候选；不自行重定产品目标 |
| 原型与验证 | 原型、实际观察、验证结果与限制 | Coding Harness 管代码与测试；不默认发布或开展外部用户测试 |
| 独立评审 | 绑定固定目标的 findings、证据与 verdict | 独立上下文、自行核验，不改被审目标或自行合并 |
| 沉淀续接准备 | 工作记忆候选、来源与下一步材料 | 不把推断升格为决定，不自动切换当前会话 |

回应 Coding Agent 的设计边界问题，主要属于专项设计中的“设计支持 / 有界裁决”。查询已有依据可由原 Agent 或取证任务完成；技术事实由验证回答；是否通过评审由独立 reviewer 回答。沉淀材料本身不授予实现许可。

普通查询、追问或转送不必各开会话。用途分类说明会话做什么，不决定会话活多久；主题负责人可以跨多轮开发持续工作，单个请求有界并不要求负责人临时化。任务类型、创建方式、生命周期和权限分别确定；裁决不是天然全权的第六类角色。

### 4.3 有界委派

上下文充分与获得权限是两个独立条件。同角色续接延续既有身份；辅助任务提供证据或建议；有界裁决委派才允许在指定范围内作决定。

候选默认是把设计问题交给已有的主题负责人，而不是每个功能或每轮开发另建一个设计师。负责人覆盖哪个主题，与某次请求允许解决什么是两层范围；前者不会因一个实现任务结束而自动消失，后者必须有明确边界。需要额外委派时，可在工作交付点指定辅助工作与权限，不让用户逐条配置或每天维护忙闲开关。未被委派的决定仍归原设计负责人。

#### 4.3.1 接入已有主题负责人

从用户现有的主题对话开始，不要求先建立团队组织树或搬家。候选入口是 Shuttle 中的“接入设计协作”，将有权方确认的已有角色与当前对话关联；不是仅凭改名就把任意对话变成有裁决权的负责人。

| 时机 | 用户需要确认什么 | 不重复承担什么 |
| --- | --- | --- |
| 主题首次接入 | 所属项目与主题、现有设计资料、允许哪些已关联工作向此处提问和接回答复 | 不重新粘贴整段历史，不设置每日忙闲状态 |
| 开发任务首次关联 | 本任务的问题交给哪个已有主题负责人；优先沿用任务 / 交接中已明确的设计来源 | 不找浏览器窗口，不在每次提问时再选收件人 |
| 正常提问与追问 | 已有范围内无需再次设置；范围有变化时另行确认 | 不重建身份，不手工中继材料和答复 |

界面从用户指定的任务和资料中预填简短说明，并保留来源供核对；缺失或有歧义的字段才询问，不扫描全部私人会话推测分工。主题名称仅用于理解，不足以决定路由：例如“整体设计”和“响应模块设计”不能因名字存在层次，就自动成为上级和下级。无法确定目标时保留问题、显示待确认，不广播到所有可能的对话。

接入时分开说明两件事：允许按约定自动投递和回传，与角色可作哪些设计决定。前者不扩大后者。对已有设计的解释、候选建议和授权范围内的裁决保留各自性质；范围改变或人类保留决定仍走已有授权路径，不用一个笼统的“自动协作”开关包办。

开发任务可看到稳定的设计来源，例如“设计请求交给：响应模块设计”；窗口关闭、刷新或改名不意味着职责撤销，也不应丢失待办。尚未具备安全投递条件时显示等待或阻塞，不因关联成功就宣称可执行。换到新对话属于已有角色的续接与绑定变更，不能把重复窗口当成第二个当前负责人。

这一入口只描述产品体验，不预设业务主题与 Work Item / Logical Thread 一一对应，也不新增全局角色注册表。需复用现有身份、唯一绑定与路由规则；多主题映射及其与 v3 `PRIMARY_DESIGN` 范围的关系仍需在第三阶段明确，不能据此扩张当前自动执行范围。

#### 4.3.2 按请求界定裁决范围

交付时需要明确以下内容；这是用户可理解的委派说明，不是新增配置表或 wire schema：

| 内容 | 要说明什么 |
| --- | --- |
| 负责的工作 | 归属哪个设计主题，本次请求对应什么原任务，以及设计回应交回哪里 |
| 使用的依据 | 已确认的设计版本、相关理由、重要未决问题和材料来源 |
| 可以决定的范围 | 哪些解释或局部设计选择已经委派，不能只写笼统的“负责设计” |
| 必须交回的边界 | 涉及哪些约束、目标、风险或范围变化时需指定设计方重新决定 |

这些内容可从已有任务和设计材料编译成简短候选说明，再由有权方明确确认；不要求用户从零填表，也不以系统生成的文本自授权限。不能从沉默、普通评论、相同模型或相同角色名推定授权。

已有确认范围可沿用，不要求每个请求重新批准一次；补充材料不能顺带扩大权限，新的范围须单独确认。路由关联解决“交给谁”，这里的范围解决“能决定什么”，不能相互替代。

#### 4.3.3 额外委派与生命周期

已有明确委派、充分材料和安全通道时，可由工作会话处理指定问题，不占用主讨论。缺少任一条件，或请求超出职责时，仍回到指定设计方。并行能力需实测，不以第二个窗口存在作为证明。

该方案不是对“不默认另开临时设计师”的撤销，也不改变当前主设计路由；是否采用仍待确认。若使用 child worker，复用已有身份和结果返回语义，不冒用父角色或创建第二个当前主会话。

额外委派的生命周期跟随被委派工作；工作结束或委派撤回后不再接收新的委派请求。原主题负责人独立延续，不因一条消息答完或一个开发任务结束而被关闭，也不因此无限扩展职责。主题换会话、关闭或重新分工时，未完成请求必须保留或明确移交。具体生命周期映射仍需对照已有契约。

## 6. 验收关注点（待场景验证）

- 换会话后能继续工作，无需用户重讲整个项目；未完成请求不丢失。
- 接收方得到足够且聚焦的材料，旧建议不被误当成已确认决定。
- 请求、补充材料和结果均可往返原任务，不靠用户中继。
- 已指定的主题与开发任务能沿用设计来源，正常提问无需重复配置；主题命名或接入操作不会隐式扩大权限。
- 当前回应不被普通新请求强行中断；用户留在主题中也可接续处理已授权的外部请求。
- 生成期间可编辑和提交下一条，能辨认正在处理谁与待发顺序；草稿、排队输入和已提交内容不混淆。
- 中断、绕行输入及提交竞态不造成错误回传或请求丢失，缺乏安全通道时诚实展示阻塞。
- 无委派时不能冒用角色权力；依据变化后不能直接沿用旧结果。
- 失败保留材料，可恢复且不重复执行；实际操作成本低于人工传话。
