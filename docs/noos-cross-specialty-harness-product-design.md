## 1. 如何继续这份设计（本对话工作记忆）

用户约定原文：

> “我一边讨论，你一边把一些点就往设计文档里面去改。然后改着改着达到了一个相对稳定的程度就形成提交，防止聊着聊着把前面的东西又忘了。”

后续本任务按以下方式持续推进：

1. 每轮聚焦一个问题，先读本文相关共识与未决项，再讨论；不要求用户重述整个项目。
2. 当轮形成的共识、理由、未决问题及变更原因及时更新本文，不为每轮讨论另建 amendment。
3. 明确区分用户已确认方向、助手建议、开放问题与既有契约；用户批准讨论计划不等于接受全部候选方案。
4. 已确认内容发生变化时，记录新依据与取代关系；不悄悄删除此前的关键取舍理由。
5. 一组设计相对稳定后做本地阶段提交。本次计划授权阶段性提交，不授权自动 push、建远端 PR、merge、部署或关单。
6. 稳定方案按仓库流程接受独立评审；触及契约时另行提交裁定。检查点提交不等于评审 APPROVE。
7. 本文是跨会话可恢复的工作记忆，不声称聊天平台已保存永久 memory；原对话保留为来源，不整段复制为主要设计输入。

恢复入口：当前在第二阶段场景 B1，并提前探索第三阶段的委派边界。已确认授权范围内自动触发、忙碌排队不抢占；默认手动忙闲开关建议已撤回。四个历史请求已完成过程推演。最新候选区分“材料不足”和“没有裁决权”，建议在任务交付时明确有界委派，而非按消息临时复制设计师；这是待用户确认的新方案，不改变当前主设计路由。安全处理时机、GitHub 分工、具体授权配置及首版优先级仍未定。

## 2. 已确认的产品方向

### 2.1 两个出发点

- 用户希望保留 ChatGPT 网页版作为深度思考、产品讨论的场所，通过外部支撑补足工作连续性与行动循环，而不是为了执行能力被迫迁往另一种讨论体验。
- 用户希望减少 Chatbot、Coding Agent、视觉创作工具之间反复搬运材料、解释背景、转送结果的负担。

上述 ChatGPT 偏好来自用户的使用体验，不是跨产品能力评测结论，也不以某个平台永久缺少某项功能为产品前提。

### 2.2 产品定位与命名

用户对职责归属的原文：

> “Coding 内部的 Harness 他们自己管。”

> “Design 内部的 Harness 由于发生在 ChatGPT 这种 chatbot 里面，我们就来接管。”

> “或者准确地来说，是 Noos Hub 来接管。Noos Shuttle 是浏览器当中跟 Chatbot 和画图工具桥接的一个桥梁，一个交互界面。”

据此沉淀的产品方向：**NOOS Hub 是跨专业工作过程的 Harness 中枢；NOOS Shuttle 是浏览器侧的桥梁与交互界面。**

Hub 的目标覆盖深度调研与讨论、产品设计、视觉创作、代码实现、原型验证之间的工作循环；不是要求某一个模型或工具承担全部过程，也不是把所有工具已有的内部执行机制重做一遍。

| 领域 | 已确认方向 | 尚未确定的深度 |
| --- | --- | --- |
| Coding 内部 | Coding Agent 自管内部 Harness | Hub 与其交互的最小任务、状态和结果接口 |
| Design 内部 | Hub 为 Chatbot 补足工作连续性及外部行动能力 | 自动沉淀、换会话、委派与恢复各自的权限和触发方式 |
| 视觉创作内部 | 纳入整体产品方向，倾向由 Hub 补足 | 接管范围、工具能力、素材与版本交互，后续专项设计 |
| 跨专业协作 | Hub 管理各专业之间的协作循环 | 分工建立、并行依赖、结果接纳和人工决定点 |
| 浏览器交互 | Shuttle 连接 Chatbot 与视觉工具 | 具体操作能力依平台验证，不预设万能适配器 |

ChatGPT 是重点入口，不是永久唯一的工作中心。专业角色可以持续负责各自领域，用户的工作不绑定单一工具。

### 2.3 团队式协作与上下文隔离

用户原文：

> “搞设计的，就专门搞设计，搞开发的就专门搞开发，让他们的上下文维持相对隔离”

设计取向是专业化协作：角色通过任务、决定、证据和结果连接，不默认共享所有聊天历史。理由是减少无关材料、过时意见与不同角色目标互相干扰；不把这一动机当作未经验证的模型性能定律。

隔离不等于不能追问或查阅来源。具体共享范围、补充上下文的方式及成本，留待第三阶段确定。

### 2.4 三种用途不混用

| 用途 | 要保留或传递的连续性 | 不应被等同为 |
| --- | --- | --- |
| 同角色跨会话续接 | 先沉淀，再到新对话继续同一角色的工作，产生类似 compact 的效果 | 将全部旧对话重新灌入，或自动转交另一角色 |
| 跨角色交接 | 保持分工，交付对方需要的任务、依据、约束和结果 | 将发送方的全部工作记忆复制给接收方 |
| 知识沉淀 | 保存可复用结论供未来工作使用 | 默认启动任务、切换会话或授予执行权限 |

既有 Crystal 可提供续接所需的部分材料，但是否足以承载角色工作记忆需要验证，本文不改变其既有定义。

## 5. 后续讨论与阶段检查点

### 第二阶段：真实场景与优先级

原计划按以下顺序讨论；可随用户提供的具体材料调整讨论入口，不据此预定实现顺序：

| 场景 | 已知用户动机 | 下一轮要补齐的事实 |
| --- | --- | --- |
| A：设计讨论换新对话继续 | 先沉淀，再迁移，实现类似 compact 的工作记忆续接 | 最近一次实际换对话的原因、携带材料、丢失内容与重述成本 |
| B：设计向开发或视觉角色交付并接回结果 | 专业上下文相对隔离，避免人工搬运 | 一次真实交付的输入、完成标准、追问过程及接收结果方式 |
| C：调研到原型验证再返回设计 | 打通不同工具不能单独覆盖的全过程 | 选择一项实际产品工作，识别迭代、并行、返工和人工决定点 |

每个场景补齐：用户目标、角色分工、必要上下文、交付物、人工决定点、完成标准、失败恢复方式。用用户确认的实例记录旅程，不代填为已验证事实。

退出条件：三个场景已讨论并得到用户确认；首版必需能力、优先级与后续扩展明确。届时形成第二笔设计提交。

#### 场景 B1：开发遇到权限边界，向设计方请求裁决

来源：用户在本设计对话以“看看这种情况”提供的附件《已粘贴的文本.txt》，开头为“继续收敛的话，我建议先把协议钉死”。原附件包含 `Adjudication Request / Result Contract v0` 候选及 transport client 建议。本节保存必要内容与分析，不依赖该附件的本机路径才能恢复讨论。

来源性质：这是一份候选方案，不是已运行事件日志、已批准契约或实施授权。材料中的“只实现 transport client”等句子是被讨论的内容，不触发本任务执行。以下产品解读尚待用户确认。

材料提出的核心目标原文：

> “让 CC 在遇到 Authority Boundary 时，可以自己把问题送到 GitHub；裁决方只需要读取 GitHub；CC 再自己把裁决结果取回来。”

| 旅程要素 | 材料中的方案 | 待核实或补充 |
| --- | --- | --- |
| 用户目标 | 减少裁决请求与答复的人工复制粘贴 | 已确认仍需人来回传话；需要自动触发与顺畅传递，具体授权范围待定 |
| 角色分工 | Execution Agent 提问并执行；Adjudicator 给有边界的决定，不代写 patch | 实际裁决方及其授权如何指定？ |
| 必要上下文 | 单一问题、exact target、权限边界、假设、候选方案与证据指针 | 设计方能否直接读取来源？材料不足时如何追问？ |
| 交付物 | 持久 Request；绑定请求与目标的 Result；修改后的应用记录 | 与既有 Escalation、HandoffPacket、WorkerResult 等的对应尚未核对 |
| 人工决定点 | 原附件暂由人说“go / 看裁决队列”触发；涉及保留权限时停下 | 本轮用户确认产品应消除逐次点击：指定角色与授权范围后自动触发思考、答复；越权决定找用户 |
| 完成标准 | 原开发任务取得适用裁决后继续、修改或停止，并保留来源 | 收到、确认适用、执行完毕必须区分；完成定义待讨论 |
| 异常路径 | 依据冲突、结果歧义、目标变化或权限不足时停止或重新裁决 | 发送失败、重复投递、长期无答复、裁决会话更换的用户恢复路径尚未写清 |

产品解读（助手建议）：这不是把工作主场整体迁到设计端，而是保持两个专业角色的工作上下文，在一个明确阻塞点进行往返协作。Hub 的候选价值是保存“哪项工作在等谁解决哪个问题”的连续性，不要求设计方接管编码细节。

与同角色续接的交叉场景（待推演）：请求未完成时，设计角色换了聊天窗口，新窗口需要知道这笔待处理事项及其依据；原开发任务应仍能找到返回结果。这里需要区分角色的工作记忆与待办事项的持久记录，不能只靠聊天摘要隐含继承。

在考虑协议采用前需核对的风险，不作为本轮正式 review finding：

- 候选里的 `status: RESOLVED` 来自 Result，不能直接等同于既有 Escalation 已通过授权 reducer 完成 resolution；传输收件不是自动放行。
- `authority sufficient`、`target_sha compatible` 仍是需要明确定义的检查条件，不能仅凭字段名承诺 deterministic resume。
- 材料 §6 允许证明兼容后消费，末尾又建议 v0 不自动判断兼容；后续必须澄清首版规则，而不是把两段一起当定案。
- “不做 Governor”只限制首版范围，并未消除谁有权裁决、谁可接纳和谁能恢复执行的问题。复用既有契约，不新增平行状态控制面。

用户补充确认原文：

> “需要我来回传话。这里就涉及到，怎么能自动触发，怎么能顺畅传递”

这确认为真实使用痛点：即使请求和结果已能持久保存，用户仍需往返提醒各角色读取和处理。不能只把复制长文改成反复发送“去看看”，就宣称完成了跨角色协作自动化。尚无运行日志证明具体失败率或耗时。

#### B1 自动触发与投递（产品方向已确认，具体机制待定）

用户通过本对话批注对以下问题回答“是啊”：

> “你是否希望指定好设计角色后，开发请求能直接触发它思考并答复，不再逐次等你点击？涉及超出授权的决定，再停下来找你。”

因此，B1 的产品方向确认为：预先指定角色与授权范围后，请求能够自动触发设计方处理和答复，不要求用户每次发出开始指令。此确认不等于批准具体适配器方案，不是本次会话启用监控、自动提交网页消息或解除执行门禁的授权。

将触发分成三个边界，避免把“能收到消息”误当成“可自动执行”：

1. 发现与路由：Hub 发现已登记协作关系中的有效请求，绑定原任务和预先指定的目标角色；任意评论不构成授权，不能凭文本自称角色获得路由权限。
2. 唤醒与处理：目标角色可用时，通过其适配器触发读取、讨论或答复；是否允许自动提交一轮消息，应来自用户事先授予的范围，而不是请求内容本身。
3. 返回与后续动作：结果自动回到原任务；语义接纳、修改、恢复执行仍遵循既有权限与门禁。自动投递不自动放行。

已确认体验目标：用户先指定角色及自动处理范围，正常请求不再逐次人工转送或点击启动；超出授权的决定仍交给用户。助手建议的配套体验：Hub 展示等待对象及原因，目标无法唤醒或故障需干预时请求介入。首版交付范围与具体机制仍待确定。

顺畅传递的候选要求：

- 接收方得到聚焦问题、必要约束与可访问的依据，而非默认整个历史；无法读取引用时明确缺口，不假装已掌握证据。
- 发送、被接收、产生答复、答复被接纳分别可观察，不用“已发送”代替“已处理”。
- 目标正在生成或用户正在输入时不抢占；等待合适时机的具体策略待定，沿用现有 readiness / control 语义，不增设平行控制面。
- 失败重试不重复创建逻辑任务；发送结果不确定时先核实，不能盲目再发。目标会话更换后仍指向同一角色和原任务。
- 目标关闭或不支持安全唤醒时保留待办并显示原因；是否自动打开会话须另行确认并验证平台能力。

轮询或 webhook 是发现机制的选择，不能替代上述产品闭环。尚不选择实现机制，也不启用任何后台监控。

用户随后对以下建议回答“赞同”：

> “先排队、不抢占当前讨论，在安全的时机自动处理；不要默认另开一个缺少设计背景的‘临时设计师’。”

据此确认：角色忙碌时保留请求并排队，不抢占用户当前讨论；安全时机到来后，在已授权范围内自动处理，而不是重新要求每次点击。不开独立临时会话作为默认绕过手段。这是产品行为方向，具体队列实现仍复用既有运行机制。

下一项待确认：什么是可安全接单的时机？页面一轮生成结束只说明生成停止，不能证明用户已经结束当前讨论。如何表达用户仍在使用该设计角色、何时允许接单，以及如何避免请求长期等待，仍需设计；不在本稿擅自指定超时或空闲判定规则。

#### B1 深度推敲：不让用户管理忙闲，也不制造平行设计权威

来源：助手曾建议用户切换“正在与我讨论 / 可自动接单”，用户追问“这样操作会不会很繁琐？容易忘？”，随后要求“深度推敲”。助手撤回把手动切换作为默认交互的建议。以下是新的设计分析，不是用户对替代机制的批准。

**问题拆分。** 页面是否能输入、用户是否愿意被打断、目标是否具备充分上下文、目标是否有权做出决定，是四个不同问题。生成结束、标签页失焦、若干分钟无输入都不能单独证明后三项成立。不能通过不断增加空闲检测规则，把不确定的人类意图包装成确定授权。

在普通单一聊天窗口缺少可靠并行或调度能力的情况下，不能同时承诺：只使用原会话、立即自动处理外部请求、绝不干扰人的当前思考、完全不需要表达交接意图。排队允许等待，本身不违背自动触发目标；但永久等不到时机也不能宣称协作闭环完成。

| 候选方案 | 好处 | 隐性成本与本轮判断 |
| --- | --- | --- |
| 用户维护忙闲开关 | 表面上容易识别投递许可 | 忘记切回会导致长期积压或突然插话；撤回作为默认交互的建议 |
| 无操作一段时间就投递原窗口 | 用户不需要设置状态 | 会把阅读、思考、看其他材料误当作结束；不作为安全或授权依据 |
| 所有请求都等待主设计会话 | 保留最完整的潜在上下文和单一裁决来源 | 存在队头阻塞；应显式展示原因，不能用通知轰炸假装自动化 |
| 每个请求临时生成一个完整设计师 | 容易并行、不占主讨论 | 压缩丢失理由、过期依据、重复 token 成本与裁决分叉；不建议作为默认 |
| 有边界的辅助工作 + 指定裁决方 | 可提前取证、整理问题，减少真正决策时的负担 | 必须准备角色材料、限定权限、处理依据变化；推荐探索，但具体委派仍需授权及契约适配 |

**候选方向：让可独立完成的工作先推进，而不是让 Hub 猜用户何时结束思考。**

- 自动收件、去重、原任务关联、按授权路由、持久保留待办与结果返回属于运行管理；不要求每个步骤都占用主设计对话。
- 在工具能力和授权允许时，辅助任务可以读取被指定的材料、检查缺口、整理证据、拟定答复；这些产物是建议，不冒充主设计裁决。
- 明确可由现有依据直接回答的问题，可以在预先规定的能力与权限范围内交付引用；不能让来源 agent 或 Hub 凭自然语言自评“只是解释”就降级真正的 authority boundary。
- 改变约束、解决相互冲突的设计依据或依赖尚未沉淀的讨论时，交给指定裁决方。等待时可准备材料，不能复制一个同权设计师消除等待。

这里的任务类别是解释产品行为的例子，不是给 ResolutionPolicy 新增语义分类器，也不是批准新的自动恢复规则。哪些具体请求可自动答复，应由后续明确的授权与既有机制约束。

**角色与会话的潜在扩展。** 长期可探索“交互讨论场所”和“受管工作会话”分开，但不能把两者称为天然同步的同一个大脑。辅助会话必须绑定具体任务、已授权职责及固定材料版本；它不因拥有相同角色名称而取得裁决权。这与用户已确认的“不默认另开缺背景的临时设计师”有兼容的受限解释，但新增工作会话不是本轮已批准方案，也不能代替既有主设计路由。

工作记忆使有边界的委派成为可能，但不证明能完整复制原会话的推理质量。材料至少需要能指明适用决定、相关理由、已知未决问题和禁止自行作主的范围；具体内容待场景验证，不预设新 schema。若材料不足，返回缺口而不是默认灌入全量历史。

**并行的真正风险是依据变化。** 例如主对话正在探索“取消登录”，开发请求仍基于当前登录方案：

- 新想法尚是候选时，不能被自动升级为新执行依据；工作侧只能声明其所用的已授权版本。
- 如果当前阶段必须暂停相关实施，需要形成明确的范围/授权变化，不能指望 Hub 从闲聊中猜出来。
- 一旦适用依据已通过授权变更，原结果能否被接纳必须重新检查；不因为结果较新或已经发到 GitHub 就自动适用。

该例是压力推演，不是要求立即自动判定 topic overlap 或 target compatibility。

**用户体验目标（建议）。** 用户不维护每条请求的忙闲状态；默认只看到有意义的状态，如“正在整理依据”“等待设计决定”“需要补充材料”。这些是既有事实的展示，不引入第二套生命周期。只有真正的决定或无法恢复的运行阻塞才需要介入；聚合提示而非逐条打断，等待时长只影响提醒，不提升权限。支持暂停自动工作作为可选控制，不让暂停/恢复成为每日正确操作的前提。

**验证这条路的最小推演：**

| 情形 | 应验证的行为 |
| --- | --- |
| 用户读完答复停顿，但还在思考 | 不因无键盘输入而把后台任务插入原讨论 |
| 开发请求只缺一份既定依据 | 能否在授权范围内准备或返回该依据，而不必唤醒主设计方重新解释 |
| 请求必须改变设计决定 | 交指定裁决方；辅助任务不得自升格为批准方 |
| 辅助任务进行中，正式依据变化 | 返回结果保留原依据版本，接纳时不自动忽略变化 |
| 原对话换新、请求迟到或重复 | 角色与原任务关联不丢失；不重复执行、不误送给已失效会话 |
| 没有安全的辅助会话或输入通道 | 保留请求、展示真实阻塞，走人工辅助路径；不声称已自动处理 |

下一步建议：先用真实请求验证“有界准备是否足以减少主设计方负担”，再决定是否需要受管辅助会话；不是先实现多个设计师再想办法同步。不能承诺消灭所有等待，目标是消除人工搬运和无意义确认，将人的注意力留给真正无法委派的决定。

#### B1 历史请求推演：准备与裁决通常在同一请求内

执行来源：用户在上一轮建议后回复“go”，本轮据此继续文档分析，不解释为 provider GO、运行自动化或实现授权。

本轮选取四个仓库内真实提案，并与[人工协作基线的 Trace A / B](deliberation-harness/cross-agent-handoff-manual-dogfood-baseline-v0.md)交叉阅读。来源均按本文页首仓库基线读取。原提案保留的“待裁定”字样不是今天仍未解决的证据；本轮只分析历史协作负担，不重新裁定或复审这些已处理议题。下列“可准备工作”是反事实产品推演，不是已实现能力或实际节省时间的测量。

| 历史请求与来源事实 | 原 Agent 或经授权辅助任务可先准备 | 必须保留的裁决边界 |
| --- | --- | --- |
| [结果回传走哪条账本](deliberation-harness/v1-design-proposal-result-delivery-lane.md)：提案列出独立账本与 SubmissionOperation 两种解释；Trace A 记载部分疑问来自过时依据，后续明确回传复用 SubmissionOperation | 固定该工作适用的依据，列出不同文档的版本、身份与回执对应关系，返回相关原文；已有适用裁决可作为证据补齐 | 找到较新文档不等于工作自动采用新基线；若适用性或跨契约解释仍有争议，不能自行移除 blocker |
| [HarnessReducer 定位](deliberation-harness/v1-design-proposal-reducer-model.md)：提案从实现缺少 delta / ApplyResult 等机制推断其可能属于另一领域；Trace A 记载设计方不接受用缺实现来重定义职责 | 整理“契约要求 / 代码现状 / 缺口证据”的对照，把可观察事实与作者建议分开 | 缺实现不是改变体系定位的授权；是否修改契约、迁移实现或改变范围仍由指定角色决定 |
| [W11 代次与执行身份](deliberation-harness/w11-settle-hop-design.md)：提出 A/B/C 方案，文末实现记录又说明裁定后的收窄，不是简单照搬最初建议 | 提取两侧编号来源、冲突路径、受影响范围和各方案代价，给出可核对证据 | 谁产生权威执行身份及如何关联证据是结构决定，不能靠名称相近或“选最简单方案”自动答复 |
| [FORKED 能力缺口](deliberation-harness/v1-design-proposal-fork-adapter-gap.md)：同一提案混合当时 adapter 是否具备能力的事实问题，以及能否改变 creation mode 语义的设计问题；Trace B 后续区分创建来源与上下文保真度 | 核对指定代码版本的能力、收集经授权验证结果、列出可行替代方式及保真损失；不将历史缺口说成当前平台仍缺此能力 | 新会话加材料是否可满足既有要求、是否需调整约束或人工路径，不能由“暂时做不到”直接推导 |

从这个定向样本得到的设计推论（助手建议，待确认）：

1. 不应把整条请求硬分为“查资料”或“需要设计”。同一请求内可以先收集证据、补齐依赖，再保留真正待决的部分；这不是新增自动语义分类门禁。
2. 发起请求的 Coding Agent 已具备代码阅读与验证能力。默认由它准备边界问题所需的材料；Hub 提供持久记录、传递与返回，不接管 coding 内部 Harness，不默认每条请求再启动一个助手。
3. 并非所有请求都能免除设计判断。减少的是重复取材、找人和传话成本，不能据此宣称已解决“主设计对话忙碌时怎样安全自动开工”。
4. 查到既有裁决可以减少重复讨论，但必须核对适用范围与工作依据；不会因为内容相似就自动判定当前 Escalation 已解决。
5. 这四条是从已升级的设计请求中选取的定向案例，不代表全部请求的分布，不能推算自动答复率或吞吐收益。

**最小闭环推演：**

- 原 Agent 持久提交有界问题与依据；按已有约束停止越过相应边界，不凭本稿扩大或缩小停止范围。
- Hub 记录并路由到已指定设计角色；可检查身份、引用、重复记录等结构信息，但不裁定设计答案或生成新的 authority。
- 材料不足时，设计方的追问自动沿原任务返回，由原 Agent 补充；重要补充进入同一可追溯协作记录，用户不担任中继。准备不能变成无期限的“材料完美后才能提问”门槛。
- 设计方在安全、授权的处理条件下形成决定；结果自动返回。接收后的应用、恢复执行仍受现有契约约束，不把收到结果视为已放行。

这里不要求新增后台设计会话；若以后明确出现并行取证需求，再评估受管辅助任务。请求已经登记但设计方尚未处理，不能显示为“正在裁决”；设计方要求补充材料，也不能显示为“已解决”。

**尚未闭合的主问题：** 上述推演可以消除来回传话，并减少材料准备负担，但无法从历史提案证明有一个可靠的、不需用户切换状态的主会话自动处理时机。后续仍需在可验证的 provider 调度能力、明确委派的独立工作会话或低频人工交接之间做产品取舍；不得把本轮“go”或对自动触发的目标确认解释为已选择其中一种。

#### GitHub / Hub / Shuttle 承载分工（助手建议，待确认）

用户要求进一步区分哪些内容适合 GitHub 中转、哪些由 Hub 和 Shuttle 管理。这是设计问题，不是批准全部内容上云或采用双向全量同步。

候选原则：GitHub 承载适合共享、异步读取、与仓库版本关联的协作记录；Hub 管理工作连续性、选择性上下文投递及运行控制；Shuttle 负责浏览器端实际交互与观察。GitHub 是可选协作后端，不是所有产品工作必经的总线。

| 内容或动作 | 候选承载方 | 边界 |
| --- | --- | --- |
| 仓库相关的有界问题、正式裁决答复、review、验收证据 | GitHub issue / PR / repo 文件 | 经授权发布必要内容；引用 exact revision；评论本身不授予设计或执行权限 |
| 尚未正式采纳的跨角色追问与补充证据 | 随所属任务的协作后端 | 仓库任务可沿原线程记录；影响裁决前提的补充不得只留临时消息；纯进度噪声不必逐条发评论 |
| 角色对应哪个会话、窗口是否可用、何时可投递、重试与收件确认 | Hub 的既有运行机制 | 不能从 GitHub label 或“已回复”推断运行状态；Shuttle 上报浏览器观察 |
| 长对话原文、角色工作记忆、未公开访谈和探索草稿 | Hub / 本地 Vault，选择性投递 | 不默认上传 GitHub，也不默认完整交给下一角色；外发仍需匹配授权与隐私范围 |
| 图片、素材、生成版本与创作工程 | Hub 管索引、来源关系和存储引用，实体位置依创作工具另定 | 可将选定版本与验收依据引用到 GitHub，不预设所有二进制素材进入 repo |
| 页面输入、附件投递、结果捕获、生成状态观察 | Shuttle | 不持有独立任务真源，不自行决定裁决是否足够或是否恢复开发 |

避免双重真源：对每类事实明确责任，而不是要求所有信息都只存一个位置。GitHub 上的已发布内容是共享来源；Hub 保存其不可变观察与投递关联，并按既有 reducer 管运行事实。内容已发布、浏览器已接收、Agent 已答复、结果已被授权接纳是不同事实，不用一个同步状态互相覆盖。正式语义权威仍来自被指定的契约与授权角色，不能从存储位置推导。

场景 B1 的候选路线：CC 通过既有授权路径登记请求，并发布最小协作记录 → Hub 发现该记录、关联原任务及目标角色 → Shuttle 在安全且授权的时机触发设计会话 → 答复经授权发布回原线程 → Hub 将结果及必要依据送回原开发任务。请求持久化、投递身份、重试和 resolution 复用既有契约，不为这一路线另立一套生命周期。

不应简单把上一行缩写成“GitHub 有新评论就自动执行”。发布与运行都需要来源核对；普通评论、编辑或重复观察不能单独授予动作权限。

原型可以先借 GitHub 跑通仓库协作，但应与长期产品依赖区分。纯设计或视觉工作不必先创建 repo / issue 才能续接、沉淀或交接；本地协作仍应可持久化，而不是仅存在浏览器内存。多设备协作与替代后端暂不设计。

恢复与隐私需进一步推演：GitHub 不可用时保留本地待投递内容并显示未发布，不假装已共享；Hub 不可用时 GitHub 记录仍在，但不能声称已唤醒目标；目标无法访问引用时明确缺口，不通过擅自上传完整私有材料绕过。

待用户确认的取舍：是否接受 GitHub 是仓库协作的默认共享记录位置，但不成为所有非 coding 工作的强制依赖？B1 自动触发方向已获确认，但不构成对此承载分工的确认。

### 第三阶段：工作记忆与协作规则

基于场景划分团队共同依据、角色记忆和历史材料，确定续接与交接各自携带的信息；明确决定、候选、否决及未决状态，以及结果接纳、依据变化和中断恢复的责任。

优先对照既有 Work Item、Logical Thread、Handoff、Crystal、Result、Context Pack；对象对应关系是待验证设计，不以名称相近直接视为等价。只有场景证明有缺口时，才提出新接口、类型或对象。

#### 从 B1 提前探索：原会话的不可替代性来自哪里（候选）

用户要求继续推敲；以下不构成已确认的组织结构或新授权机制。

原会话的优势可能是尚未沉淀的相关理由、当前未决问题、与用户正在形成的共同理解，以及被明确指定的职责。不是窗口本身天然具有权威。需要区分三类问题：

| 原会话看似不可替代的原因 | 合适的处理方向 | 不能据此推断 |
| --- | --- | --- |
| 相关依据已经持久化，只是接收方没拿到 | 编译与任务有关的材料和可核对来源 | 发一份摘要就证明对方足以裁决 |
| 相关理由或正在形成的取舍还没有沉淀 | 原角色补充可表达的工作记忆，或直接处理该问题；信息不足时保留缺口 | 捕获完整历史就等于恢复所有判断能力，更不能宣称导出了模型隐藏推理 |
| 接收方没有作这类决定的权限 | 由有权方明确委派，或继续由指定角色处理 | 使用同一模型、同一角色名、同一上下文就取得同样权力 |

由此得到的候选原则：上下文可移交与权限可委派是两个独立条件。不得用其中一个代替另一个。

#### 同角色续接、辅助任务、有界裁决委派不能混为一谈（候选）

| 行为 | 延续或新增什么 | 对主设计职责的影响 |
| --- | --- | --- |
| 同角色换新对话 | 按既有 rollover / binding 语义更换承载会话 | 延续同一工作身份，不制造两个并行的当前主会话 |
| 辅助准备 | 单独有界任务，交付证据、对照或候选建议 | 不取得设计批准权；多数代码取证仍由原 Coding Agent 完成 |
| 有界裁决委派 | 有权方将具体任务内的某类选择明确交给工作会话 | 仅在委派成立且契约允许的范围内作决定，不成为另一个通用 Primary Designer |

工作会话若采用 child worker，应复用既有身份、返回与交付语义，不冒用父角色的 Logical Thread 或直接改写其 current binding。其结果也不自动改变公共契约。任务边界之外仍回到指定设计方，保留独立评审与人类保留权限。

#### 更低操作负担的候选入口：把委派放在工作交付里

不建议让用户每天维护“忙 / 闲”模式，也不建议逐条配置每个请求。可以探索在自然交付点明确一次范围：例如用户确认一项设计并交给开发时，同时明确后续哪些解释、选项可由指定角色独立处理，哪些仍要回来讨论。自然语言可以提出该范围，但最终授权需要按现有机制明确记录；沉默、页面无操作、普通评论不构成授权。

这是一项工作持续期间的有界安排，而不是永久授予一个后台设计师全权。是否需要独立工作会话，要由并行需求、职责和材料条件决定；若原角色已能安全处理，不额外创建会话。预授权及工作会话建立均未在本次对话实际执行。

例子（假设性推演，不是新增裁定）：已确认某个原型使用两个既定布局，任务允许指定工作会话根据指定验收约束选择其中之一。它可以在范围内比较并答复；若两个布局都无法满足约束，应返回冲突，不能自行改变目标用户、删去约束或设计第三套方案并当作已批准。

判断上述内容的 agent 可以提出解释与建议，但 Hub 不承担自然语言语义审判。可否据结果解除阻塞仍依现有 ResolutionPolicy / 授权门禁，不因本节有界委派示例而自动满足。

#### 自动触发能解决什么，仍不能解决什么

如果已有明确登记、材料充分且具备安全执行通道的工作会话，Hub 可以在授权范围内将相关请求送去处理，不必判断用户是否已结束主讨论；这条路线从结构上绕开抢占同一窗口，而不是提升“猜空闲”的能力。并行 provider 能力仍需验证，不能仅凭建立第二个窗口宣称支持安全并发。

若没有这样的委派，或者请求触及主设计职责，仍沿当前 Primary Design 路由排队。不能为了满足自动响应指标悄悄开新设计师；队列也不能无限静默等待，无法安全处理时应显式报告需要交接，而非自动改变权限。

这不是对用户已确认“不默认另开临时设计师”的反转：有界委派是有待确认的新增选项，而不是默认替代。若用户不接受引入该选项，同一主会话下自动处理与不打断之间的限制仍应如实保留。

#### 代价与验证（候选）

- 成本从反复传话转为交付时梳理任务、材料与授权；若每次配置比人工传话更麻烦，方案不成立，应缩小范围而不是增加控制项。
- 材料准备、模型调用与返回消耗时间和上下文；不用“可并行”推导“更省成本”，也不默认全量继承设计历史。
- 同一范围发生新裁定时，要显式更新适用依据或撤回委派；在途结果保留旧依据，不能自动合并到新决定里。
- 不建立整套通用团队编制或复杂 Governor 作为试用前提；优先验证一个具体任务的委派是否真的减少人的介入。

最小桌面验证：主讨论持续进行时，已委派的有界问题可在工作通道处理且不污染主会话；同一任务的越界问题回到指定裁决方；换会话或依据变化不让旧授权和新结论混用；没有委派时，不能擅自绕开原角色。

下一轮需要确认的产品选择：是否接受“主设计讨论保持专注，在一项工作的明确授权范围内允许指定工作会话处理后续问题”，作为自动接单的可选方式？在确认前，单主设计路由与排队原则继续有效，本稿不宣称已解决全部自动触发场景。

退出条件：职责与信息流明确；既有设计对应表及需要裁定的差异齐备。届时形成第三笔设计提交；涉及契约的差异另走裁定，不在本文直接生效。

### 第四阶段：交互与首个产品切片

围绕第二阶段选定的最高优先级场景，设计入口、用户可见状态、交接确认、失败恢复和人工控制；不提前规定页面或按钮结构。

桌面推演必须覆盖：

- 新对话能否继续同一角色工作，无需用户重讲整个项目。
- 接收方材料是否足够，且未默认灌入无关历史。
- 旧建议是否可能误升格为已确认决定。
- 返回结果能否对应原任务，而不自动等于接纳或继续执行。
- 材料缺失、投递失败、会话失效时，材料是否保留、责任是否清楚、下一步是否可见。

退出条件：体验方案、验收场景、首个切片与非目标明确，并记录推演暴露的问题。届时形成第四笔设计提交，之后才讨论实现授权。
