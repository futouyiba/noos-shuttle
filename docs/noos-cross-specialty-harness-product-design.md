## 1. 产品定位（已确认）

**NOOS Hub 是跨专业工作过程的 Harness 中枢；NOOS Shuttle 是连接浏览器工具的桥梁与交互界面。**

服务于深度调研与讨论、产品设计、视觉创作、代码实现和原型验证之间的持续工作。核心价值是补足单一工具的工作循环，并减少工具之间反复搬运材料、重述背景和转送结果的负担。

ChatGPT 网页版是用户偏好的深度讨论入口，不是永久唯一的工作中心。该偏好不是模型能力评测，也不以某个平台永久缺少某项功能为前提。

| 层次 | 职责方向 | 保留边界 |
| --- | --- | --- |
| Coding 内部 | Coding Agent 自管内部 Harness | Hub 不重新管理代码探索、编辑和测试细节 |
| Design 内部 | Hub 为 Chatbot 补足工作连续性与外部行动循环 | 自动沉淀、委派、续接的具体机制待定 |
| 视觉创作内部 | 纳入产品方向，倾向由 Hub 补足 | 接管深度、素材与版本交互后续专项设计 |
| 跨专业协作 | Hub 管任务交付、返回与协作连续性 | 不因“中枢”定位自动取得语义裁决权 |
| 浏览器侧 | Shuttle 负责连接与交互 | 实际操作能力按平台验证，不预设万能适配器 |

专业角色保持上下文相对隔离，通过任务、决定、证据与结果协作；不默认共享全部聊天历史，也不阻止必要的追问与来源查阅。

## 2. 核心使用场景（方向已确认）

| 场景 | 目标 | 与其他场景的区别 |
| --- | --- | --- |
| 同角色续接 | 先沉淀工作记忆，再到新对话继续同一角色的工作 | 不是全量重放历史，也不是交给另一角色 |
| 跨角色交接 | 交付有边界的任务、依据、约束，接回结果 | 不是复制发送方的全部记忆 |
| 知识沉淀 | 保存可复用结论供未来工作使用 | 不默认启动任务、切换会话或授予权限 |

工作记忆与未完成协作事项不能混为一份摘要：设计角色换会话后，仍需知道哪些请求待处理、谁在等待、结果返回哪里。具体承载方式待定。

## 3. 场景 B1：开发请求设计回应

### 3.1 已确认的体验要求

- 消除用户在开发与设计之间来回传话的负担，不只是把复制长文变成反复提醒“去看看”。
- 预先指定角色及授权范围后，请求可自动触发设计方思考、答复，不逐次等待点击；超出授权的决定再交给用户。
- 设计角色忙碌时排队、不抢占当前讨论，在安全时机自动处理。
- 不默认另开一个缺少设计背景的临时设计师绕过等待。

安全处理时机尚未定义；生成结束、标签页失焦或长时间无输入，都不能单独证明用户已结束讨论或授予操作权限。

### 3.2 候选协作流程

原 Agent 准备并持久提交有界问题与依据 → Hub 关联原任务并路由 → 指定设计方处理或追问 → 补充材料与答复沿原任务自动往返 → 开发按现有授权与门禁决定后续动作。

多数代码阅读、验证与材料准备仍由原 Coding Agent 完成；不默认每个请求再启动一个助手。准备不能变成“材料完美后才允许提问”的无限门槛。

设计回应需要交代适用问题与依据、决定及理由、允许与不允许的范围。无法决定时明确缺什么或需交谁处理；设计方不默认接管 patch。

投递、接收、产生答复、授权接纳与恢复执行是不同事实。设计方追问不等于已解决，收到结果不等于自动批准继续、合并或部署。

### 3.3 候选异常体验

- 引用不可读：明确材料缺口，不擅自上传完整私有历史。
- 发送结果不确定：核实后重试，不重复创建逻辑任务。
- 会话更换：继续关联负责角色和原任务，不依赖过期窗口地址。
- 目标不可用或无法安全触发：保留待办并显示原因，不声称正在处理。
- 等待过久：聚合提示；等待时长不能扩大权限或替代裁决。
- 正式依据变化：在途结果保留原依据，接纳时不得静默沿用或自动合并。

## 4. 候选职责与工作组织

本节均待用户确认；不新增当前契约之外的运行权限。

### 4.1 GitHub、Hub 与 Shuttle

| 承载方 | 适合负责 | 不应承担 |
| --- | --- | --- |
| GitHub | 仓库相关的有界问题、正式答复、review、验收证据和重要补充材料的共享记录 | 所有私有上下文、细粒度运行状态，或仅凭评论/标签授权执行 |
| Hub / Vault | 任务关联、角色路由、投递与恢复、工作记忆、选择性材料投递、产物来源与存储引用 | 替专业角色作语义裁决，或维护与已有 reducer 冲突的控制面 |
| Shuttle | 网页输入、附件投递、状态观察、结果捕获及交互反馈 | 独立任务真源、设计批准或恢复执行的裁决 |

GitHub 可作为仓库协作的共享后端，但不成为纯设计、视觉工作或同角色续接的强制依赖。完整聊天、访谈和探索草稿默认本地保存；图片与工程文件由 Hub 管理引用和来源，实体存储依工具另定。

每类事实有明确责任方，不做无差别双向全量同步。GitHub 是共享来源，Hub 保存不可变观察与投递关联；正式权威仍来自指定契约和授权角色，不来自存储位置。外发材料需匹配授权范围。

### 4.2 工作会话的用途

按交付物分类，不是五个常驻职位或新增协议枚举。

| 用途 | 典型交付 | 边界 |
| --- | --- | --- |
| 调研取证 | 带来源的发现、反例、信息缺口 | 区分事实与推断；不擅自联系用户或外发资料 |
| 专项设计与创作 | 方案、草图、理由，或授权范围内的设计回应 | 默认提供候选；不自行重定产品目标 |
| 原型与验证 | 原型、实际观察、验证结果与限制 | Coding Harness 管代码与测试；不默认发布或开展外部用户测试 |
| 独立评审 | 绑定固定目标的 findings、证据与 verdict | 独立上下文、自行核验，不改被审目标或自行合并 |
| 沉淀续接准备 | 工作记忆候选、来源与下一步材料 | 不把推断升格为决定，不自动切换当前会话 |

回应 Coding Agent 的设计边界问题，主要属于专项设计中的“设计支持 / 有界裁决”。查询已有依据可由原 Agent 或取证任务完成；技术事实由验证回答；是否通过评审由独立 reviewer 回答。沉淀材料本身不授予实现许可。

普通查询、追问或转送不必各开会话。同一有界工作可持续追问，不等于建立永久后台设计师。任务类型、创建方式、生命周期和权限分别确定；裁决不是天然全权的第六类角色。

### 4.3 有界委派

上下文充分与获得权限是两个独立条件。同角色续接延续既有身份；辅助任务提供证据或建议；有界裁决委派才允许在指定范围内作决定。

候选入口是在一项工作交付时明确后续处理范围，而不是让用户逐条配置或每天维护忙闲开关。不能从沉默、普通评论、相同模型或相同角色名推定授权。

已有明确委派、充分材料和安全通道时，可由工作会话处理指定问题，不占用主讨论。缺少任一条件，或请求超出职责时，仍回到指定设计方。并行能力需实测，不以第二个窗口存在作为证明。

该方案不是对“不默认另开临时设计师”的撤销，也不改变当前主设计路由；是否采用仍待确认。若使用 child worker，复用已有身份和结果返回语义，不冒用父角色或创建第二个当前主会话。

## 6. 验收关注点（待场景验证）

- 换会话后能继续工作，无需用户重讲整个项目；未完成请求不丢失。
- 接收方得到足够且聚焦的材料，旧建议不被误当成已确认决定。
- 请求、补充材料和结果均可往返原任务，不靠用户中继。
- 主讨论不被后台请求抢占，缺乏安全通道时诚实展示阻塞。
- 无委派时不能冒用角色权力；依据变化后不能直接沿用旧结果。
- 失败保留材料，可恢复且不重复执行；实际操作成本低于人工传话。
