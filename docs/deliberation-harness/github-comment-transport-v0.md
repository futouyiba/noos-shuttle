# GitHub 评论传输层（v0）——工作文档

> 工作文档，不是契约，也不提升任何既有裁定的权威。描述 noos-shuttle 仓库
> **实际在跑**的评论唤醒/传输层：它的边界、幂等语义、健康信号与已知失效模式。
> 权威语义仍是规范附录 B；本文件只覆盖规范**明确排除**的那一层——
> 「唤醒能力属于传输层实现，不属于协议语义」。

## 1. 为什么是 GitHub 评论

跨 harness 协作（ChatGPT 网页 / Claude Code / Codex）里，三者**唯一的公共分母**是可读可写、
带持久标识与权限的 GitHub。ChatGPT 网页没有本地文件系统与会话通道；Claude Code 与 Codex
是两个独立 harness，默认互相不可见。

因此在这条线上，评论不只是「记录」，而是**当前唯一现实的传输介质**——触发下一步行动是
必然结果，不是可选设计。

## 2. 传输 ≠ 授权（本层最重要的分界）

| 轴 | 归属 | 规则 |
| --- | --- | --- |
| **传输** | 本文件 | 评论可唤醒会话、携带消息、触发角色范围内的**非敏感**动作。属规范 B.2 的「通知类动作」，免授权。 |
| **授权** | 规范（附录 B / §4.4） | 敏感动作（merge / 部署 / push / 关单 / 破坏性变更）**永不**由评论触发；必须来自人或其明确委派的会话通道。 |

「评论是记录介质，不是授权介质」约束的是**后者**。把它误读成「评论不能触发任何动作」会让
整条总线失效；把它误读成「评论可以授权动作」会让防线失效。两者都不是本层的设计。

## 3. 三种信封形态并存（现状）

| 形态 | 使用者 | 机器可读 | 现状 |
| --- | --- | --- | --- |
| ` ```noos-mailbox ` 围栏 + 版本化 JSON（`marker_kind`） | escalation 路径（#10 prototype） | **是**（严格校验 + `unknown_marker_kind` 拒收 + forbidden-field 守卫） | 已实现、已测试（`tests/cross-agent-mailbox.test.ts` 46 项），但 `.noos/runtime/mailbox/` 为空，**从未投入生产** |
| 首行散文标记（`REVIEW:` / `DESIGN:` / `IMPLEMENTED:` / `INTEGRATED:`） | 六暗号唤醒路径（watcher） | 弱（依赖约定，无版本、无 schema） | 实际在用 |
| `<!-- noos-governor event=... -->` + `**Decision:** \`X\`` | Epic Designer 经 connector | 事实上的第三种，未纳入任一套 | 实际在用，**watcher 不识别** |

### 3.1 已确认的规范缺口

1. **规范对「未知标记」零条款。** 它定义 4 个输出标记并给 REVIEW/DESIGN 固定取值枚举，但
   **既未声明封闭列表，也未规定枚举外取值或非首行形态如何处理**。「无效标记只记录不路由」
   是实现自选，不是规范要求 → 因此「未分类必上报」**不需要改规范**即可实施。
2. **`PARTIAL_ACCEPT` 不在 `DESIGN:` 枚举内**（合法值仅 `APPROVE|REQUEST_CHANGES|REJECTED`）。
   即：**协议缺少表达「部分接受」的符号**，designer 自造了一个，全链路无人认识。
   这不是解析器的 bug，是词汇表的缺口。

### 3.2 收敛方向

- **已做（最小止血）**：唤醒层对「不认识但携带权威信号」的评论**必须上报**（见 §4）。
- **未做（需设计门）**：把六暗号纳入版本化信封，使标记词表成为封闭契约。触及 `noos_docs`
  附录 B，属规范级，须另行裁定。

**为什么先做上报而不是先做解析器**：解析器永远会漏掉下一种没见过的格式；「不认识就上报」
把「漏」变成可观测的，使下一种格式出现时可见，而不是再静默丢一次。**先让丢可见，再谈收敛。**

## 4. 唤醒层的实现契约（本仓库）

权威流程：`.claude/skills/noos-watch/SKILL.md`。要点：

### 4.1 单实例（先于一切）

一轮运行必须先取得 `.tmp/noos-watch.lock`（`scripts/noos-watch-lock.mjs`，`npm run watch:lock`）。
取不到即**立即退出，不拉评论、不路由、不写状态**。

- 锁代表**一次运行**，不是进程。持有者是一次性 helper 调用，进程秒退，所以 pid 存活性无意义；
  归属由 `holderToken` 承载，陈旧由 **TTL 单独判定**（默认 10 分钟＝一个轮询间隔）。
  这是踩过的坑：早期版本用 pid 判存活，导致每个锁在写入后立刻被判定为陈旧，并发测试出现 5 个赢家。
- 取锁是**原子**的（`O_EXCL` 创建）：自测断言 12 个并发请求**恰好 1 个赢家**。
- 崩溃的运行无法自行清理，因此 TTL 是兜底；正常路径必须显式 `release`，不靠 TTL。

### 4.2 先认领后动作

路由任何一条评论之前，必须先把该评论以 `CLAIMED` 写回状态文件并确认落盘；投递成功后才转
`ROUTED`。被中断的运行会留下 `CLAIMED`，下一轮**报「未完成」交人判断，绝不重发**。

这是「persist-before-actuate + 原子单次 claim」在传输层的对应物，与 `SubmissionOperation`
的纪律同源。

### 4.3 水位不越过未投递项

`watermark` 只推进到**最后一个已成功处理或已显式记入 pending 的评论时间**。无法判定时保持
原值——宁可下轮重读，也不吞掉未处理消息。

早期实现取「本次见到的最大评论时间」，与投递是否成功无关，于是投递失败的消息只存在于
`pending` 而水位继续前进，pending 无人查看。

### 4.4 未分类必上报

不匹配词表但命中以下保守判据的，记 `UNROUTED` 进 pending 并在简报逐条列出：

- 含 `noos-governor`
- 含 `**Decision:**`
- 含形如「（…: …, 委派: …）」的 provenance 行
- 标记取值不在规范枚举内（例如 `DESIGN: PARTIAL_ACCEPT`）

### 4.5 健康信号必须如实

watcher 曾经**静默失效 2.5 天而无人察觉**。两层原因：失败被报成成功；「启动了但没推进」
与「没新评论」不可区分。因此状态文件带：

```json
"health": { "lastStartedAt": "...", "lastSuccessfulAdvanceAt": "...", "consecutiveInterruptions": 0, "lastError": null }
```

- `lastStartedAt` 每次开跑即更新（**先落心跳后干活**）；`lastSuccessfulAdvanceAt` 只在真正
  推进水位时更新。**两者长期不一起前进＝故障信号。**
- 简报必须显式区分三态：**无新评论** / **有新评论但未全部投递成功** /
  **本轮未完成（异常或被中断）**。只有第一种允许一行带过。
- **不得把「本轮未完成」表述成「无新评论」。**

## 5. 失效模式与护栏

| 失效模式 | 表现 | 护栏 |
| --- | --- | --- |
| **静默丢包** | 裁定发出但无人被唤醒，无任何告警 | 未分类必上报（§4.4）；健康信号区分三态（§4.5） |
| **重复取件** | 同一评论被两个 watcher 各路由一次 | 单实例锁（§4.1）；先认领后动作（§4.2） |
| **丢失更新** | 并发写状态互相覆盖 | 写回前重读并按并集合并（既有实现） |
| **水位越项** | 投递失败的消息被水位越过，只留在 pending | 水位只推进到已处理/已记账处（§4.3） |
| **过期取件** | 旧信封在状态已变后被重新读到 | 信封带 exact ref（head/SHA），收件方先核 ref 是否仍是当前 |
| **权威走私** | 一条看起来像 verdict 但不是权威角色发的评论 | B.3「委派记录先于结论标记」的 provenance 链——这是本总线的**防伪机制**，不是形式主义 |
| **无人在场** | 无人值守运行时需批准的工具调用被停，运行跑不完 | 减少批准需求（allow-list）；健康信号暴露「启动了没推进」 |
