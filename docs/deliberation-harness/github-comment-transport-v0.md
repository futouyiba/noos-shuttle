# GitHub 评论传输层（v0）——工作文档

> 工作文档，不是契约，也不提升任何既有裁定的权威。描述 noos-shuttle 仓库
> **实际在跑**的评论唤醒/传输层：它的边界、幂等语义、健康信号与已知失效模式。
> 权威语义仍是规范附录 B；本文件只覆盖规范**明确排除**的那一层——
> 「唤醒能力属于传输层实现，不属于协议语义」。

## 1. 为什么是 GitHub 评论

跨 harness 协作（ChatGPT 网页 / Claude Code / Codex）里，三者**唯一的公共分母**是可读可写、
带持久标识与权限的 GitHub。ChatGPT 网页没有本地文件系统与会话通道；Claude Code 与 Codex
是两个独立 harness，默认互相不可见。

因此在这条线上，评论不只是「记录」，而是**当前唯一现实的传输介质**——触发下一步行动是
必然结果，不是可选设计。

## 2. 传输 ≠ 授权（本层最重要的分界）

| 轴 | 归属 | 规则 |
| --- | --- | --- |
| **传输** | 本文件 | 评论可唤醒会话、携带消息、触发角色范围内的**非敏感**动作。属规范 B.2 的「通知类动作」，免授权。 |
| **授权** | 规范（附录 B / §4.4） | 敏感动作（merge / 部署 / push / 关单 / 破坏性变更）**永不**由评论触发；必须来自人或其明确委派的会话通道。 |

「评论是记录介质，不是授权介质」约束的是**后者**。把它误读成「评论不能触发任何动作」会让
整条总线失效；把它误读成「评论可以授权动作」会让防线失效。两者都不是本层的设计。

## 3. 三种信封形态并存（现状）

| 形态 | 使用者 | 机器可读 | 现状 |
| --- | --- | --- | --- |
| ` ```noos-mailbox ` 围栏 + 版本化 JSON（`marker_kind`） | escalation 路径（#10 prototype） | **是**（严格校验 + `unknown_marker_kind` 拒收 + forbidden-field 守卫） | 已实现、已测试（`tests/cross-agent-mailbox.test.ts` 46 项），但 `.noos/runtime/mailbox/` 为空，**从未投入生产** |
| 首行散文标记（`REVIEW:` / `DESIGN:` / `IMPLEMENTED:` / `INTEGRATED:`） | 六暗号唤醒路径（watcher） | 弱（依赖约定，无版本、无 schema） | 实际在用 |
| `<!-- noos-governor event=... -->` + `**Decision:** \`X\`` | Epic Designer 经 connector | 事实上的第三种，未纳入任一套 | 实际在用，**watcher 不识别** |

### 3.1 已确认的规范缺口

1. **规范对「未知标记」零条款。** 它定义 4 个输出标记并给 REVIEW/DESIGN 固定取值枚举，但
   **既未声明封闭列表，也未规定枚举外取值或非首行形态如何处理**。「无效标记只记录不路由」
   是实现自选，不是规范要求 → 因此「未分类必上报」**不需要改规范**即可实施。
2. **`PARTIAL_ACCEPT` 不在 `DESIGN:` 枚举内**（合法值仅 `APPROVE|REQUEST_CHANGES|REJECTED`）。
   即：**协议缺少表达「部分接受」的符号**，designer 自造了一个，全链路无人认识。
   这不是解析器的 bug，是词汇表的缺口。

### 3.2 收敛方向

- **已做（最小止血）**：唤醒层对「不认识但携带权威信号」的评论**必须上报**（见 §4）。
- **未做（需设计门）**：把六暗号纳入版本化信封，使标记词表成为封闭契约。触及 `noos_docs`
  附录 B，属规范级，须另行裁定。

**为什么先做上报而不是先做解析器**：解析器永远会漏掉下一种没见过的格式；「不认识就上报」
把「漏」变成可观测的，使下一种格式出现时可见，而不是再静默丢一次。**先让丢可见，再谈收敛。**

## 4. 唤醒层的实现说明（本仓库）

> 「实现说明」不是「契约」（见文首）：本节记录本仓库这一层**实际怎么跑**，
> 权威语义仍在规范附录 B。措辞不用「实现契约」，免得与文首那句自述打架、
> 被日后引用成 canonical。

权威流程：`.claude/skills/noos-watch/SKILL.md`。要点：

### 4.1 单实例（先于一切）

一轮运行必须先取得 `.tmp/noos-watch.lock`（`scripts/noos-watch-lock.mjs`，`npm run watch:lock`）。
取不到即**立即退出，不拉评论、不路由、不写状态**。

- 锁代表**一次运行**，不是进程。持有者是一次性 helper 调用，进程秒退，所以 pid 存活性无意义；
  归属由 `holderToken` 承载。这是踩过的坑：早期版本用 pid 判存活，导致每个锁在写入后立刻被判定为陈旧，并发测试出现 5 个赢家。
- **TTL 只作诊断，永不自动接管**。暂停的运行可能恢复，因此没有任何命令会回收既有锁——
  空、半写、损坏锁与遗留 `<lock>.mutation` 一律阻塞。恢复必须由人确认所有使用该路径的运行与 helper
  均已停止、不会恢复，再人工移除。
- 锁路径由 `git worktree list --porcelain -z` 定位**主 checkout** 得出（主目录 / linked worktree / 子目录同一把锁）；
  取得后所有 `refresh` / `release` 必须传同一个 `--lock-file "<绝对路径>"`，不得随 cwd 重算。
- 所有变更（取锁、续期、释放）都在一个 `mkdir` 互斥 guard 下串行化，崩溃的 guard 同样 fail closed：
  自测断言 12 个并发请求**恰好 1 个赢家**，且并发方对空 / 半写 / 损坏 / 陈旧锁**均不接管、不改写**。

### 4.2 先认领后动作（`CLAIMED` / `ROUTED` / `DISMISSED` 三态）

路由任何一条评论之前，必须先把该评论以 `CLAIMED` 写回状态文件并确认落盘；投递成功后才转
`ROUTED`。被中断的运行会留下 `CLAIMED`，下一轮**报「未完成」交人判断，绝不重发**。

这是「persist-before-actuate + 原子单次 claim」在传输层的对应物，与 `SubmissionOperation`
的纪律同源。

**新增终态 `DISMISSED`（2026-09-20）**。原先 `CLAIMED` 是唯一一个「已认领、未投递」的活
状态，于是**「我判定不投递」与「我投递失败/被中断」在状态里长得一样**，而按 skill 步骤 3
它每轮都要报成「未完成投递」交人判断——人工分诊成本随轮次无上限复现。实测：39 条 pending
中 38 条停在 `CLAIMED`，其中 11 条是合规 B.3 委派记录（`action` 字面已写「记录不路由」，
即 watcher 早已正确判定不路由，却因词表没有终态而每轮重报一次）。

现在两个终态语义不同、后果一致：

| 状态 | 含义 | 进「未完成投递」？ |
| --- | --- | --- |
| `CLAIMED` | 认领了，结果未知（可能是上轮被中断在投递中途） | **是**（欠账） |
| `UNROUTED` | 未分类，等人工分类 | **是**（欠账） |
| `ROUTED` | 已投递 | 否 |
| `DISMISSED` | 已作出**结论**：不投递（`dismissRule` / `dismissedAt` / `dismissReason` 可审计） | 否 |

判终态**不经过 `CLAIMED`**（它不触发任何投递），但写回同样必须持锁。

### 4.3 水位不越过未投递项

`watermark` 只推进到**最后一个已成功处理或已显式记入 pending 的评论时间**。无法判定时保持
原值——宁可下轮重读，也不吞掉未处理消息。

早期实现取「本次见到的最大评论时间」，与投递是否成功无关，于是投递失败的消息只存在于
`pending` 而水位继续前进，pending 无人查看。

### 4.4 未分类必上报（且「未分类」严格不含「已判定不路由」）

分类是**三选一、互斥且穷尽**：被路由表命中 → 投递；命中终态判据 D1–D5 → `DISMISSED`；
两者都不中 → `UNROUTED` 进 pending 并逐条上报。判据见 `noos-watch` skill 步骤 3，
可执行定义在 `scripts/noos-watch-state.mjs`。

不匹配词表但命中以下保守判据的，记 `UNROUTED` 进 pending 并在简报逐条列出：

- 含 `noos-governor`
- 含 `**Decision:**`
- 含形如「（…: …, 委派: …）」的 provenance 行，**且首行不是角色前缀的 B.3 委派记录**
- `DESIGN:` / `REVIEW:` / `INTEGRATED:` 取值不在规范枚举内（例如 `DESIGN: PARTIAL_ACCEPT`）

**终态判据（D1–D5）**，全部是闭集匹配，命中不了就落回上面的未分类：

| 判据 | 命中条件 |
| --- | --- |
| **D1** 委派记录 | 首行匹配 `^(orch\|impl\|rev\|des\|intg)\s*[:：]`——B.3 委派记录是唤醒行，不是 verdict |
| **D2** 已知标记、无唤醒动作 | 首行是规范已知标记但路由表未定义动作，**当前仅 `IMPLEMENTED:`** |
| **D3** 被同线程更晚的收敛 verdict 取代 | 本条的 `REQUEST_CHANGES`/`REJECTED` 之后，同线程出现 commentId 更大的逐字 `APPROVE` |
| **D4** 无匹配接收方且已记录原因 | 条目上已有 `recipient: null` + `recipientNote`，且该原因是线程的结构性事实（非暂时性查找失败） |
| **D5** 合并交接已无对象 | 本条的 `APPROVE` 之后，同线程已有 commentId 更大的 `INTEGRATED:` 记录 |

D2 与第三、四条判据是**修两条自我触发的规则打架**：`IMPLEMENTED:` 原本只出现在「未分类」
判据里、不在路由表里，于是一个正牌 B.3 标记被自己的上报规则捞起来；provenance 行判据又
与 B.3「每条委派记录都带 provenance 行」冲突，写一条合规委派记录＝自动给自己造一条 pending。

**判据不得越界**：枚举外的 `REVIEW:` / `DESIGN:` 取值（如 `APPROVE WITH FINDINGS`）、
designer 自由文本裁定、`noos-governor` / `**Decision:**` 记录，**一条都不适用 D1–D5**，
必须继续进 pending 等人工分类——那是规范侧的枚举缺口（§3.1），不是本层可以自动判掉的东西。
「未分类必上报」这条护栏完整保留：**未知** 与 **已判定不路由** 是两件事。

**投影倒向多报（fail-open）**。`scripts/noos-watch-state.mjs` 的 `projectBriefing` 是纯函数，
只看状态文件，所以它拿不到评论正文。这带来一处必须写明的分工：

- **body 级护栏（`noos-governor` / `**Decision:**` / provenance 行）始终是 skill 侧的义务**，
  投影不为它兜底、也兜不住。skill 步骤 3 因此要求 pending 条目必须记 `marker`（首行原文），
  让投影至少能复算「这一条属哪一档」。
- 认不出档位时（老条目、或没记 `marker` 的写方），投影**默认上报**，
  而不是默认沉默——本层的失败模式是**静默丢信号**，不是噪音。代价是可能把一条
  其实可路由的条目同时列进两段，宁可让人多看一眼。
- `undelivered` 同时收 `CLAIMED` 与 `UNROUTED`。今天没有写方会置 `UNROUTED`，
  但 schema 允许它：一个存在却从不进简报的状态就是静默丢信号的口子。

### 4.5 健康信号必须如实

watcher 曾经**静默失效 2.5 天而无人察觉**。两层原因：失败被报成成功；「启动了但没推进」
与「没新评论」不可区分。因此状态文件带：

```json
"health": { "lastStartedAt": "...", "lastSuccessfulAdvanceAt": "...", "lastCompletedPollAt": "...", "activeRun": null, "consecutiveInterruptions": 0, "lastError": null }
```

- `lastStartedAt` 每次开跑即更新（**先落心跳后干活**）；`lastCompletedPollAt` 在本轮完整拉取并
  记账后更新——**无新评论同样更新**。二者一起前进才说明「轮询跑完了」。
- `lastSuccessfulAdvanceAt` **只在真正推进水位时**更新。**不得用「水位没动」判断中断**：
  长期没有新评论时它本来就不动，那是正常。中断由 `activeRun` 判定——取得锁后若读到上一个
  运行留下的非空 `activeRun`，说明前一轮没走到收尾，`consecutiveInterruptions += 1`。
- 简报必须显式区分三态：**无新评论** / **有新评论但未全部投递成功** /
  **本轮未完成（异常或被中断）**。只有第一种允许一行带过。
- **不得把「本轮未完成」表述成「无新评论」。**

### 4.6 投递通道与兜底

watcher 恢复运行后暴露的第二个瓶颈：**它能跑完、能认领、能识别该唤醒谁，但送不出去。**
`ccd_session_mgmt send_message` 在无人值守的定时运行里不可用，于是每一条唤醒都只能落进
`pending` —— 检测能力恢复了，投递能力还没有。

规范 §4.4 已经给了兜底通道：**跨平台兜底通道为任务 issue 线程本身**——任何平台都可以在其上以
`role:` 前缀 + 暗号评论寻址，对应角色被唤醒后从线程拉取状态。
即：**评论既是传输介质，也是投递兜底。** 因此投递分两级：

| 级别 | 通道 | 何时使用 | 记录 |
| --- | --- | --- | --- |
| 首通道 | `send_message` 直投目标会话 | 会话可解析且通道可用 | `deliveredVia: "session"` |
| 兜底 | 在**canonical task issue** 留一条只含暗号的评论 | 首通道不可用 | `deliveredVia: "comment:<id>"` |
| 都不可用 | —— | 维持 `CLAIMED`，简报显式报「投递通道不可用」 | 不标记为已处理 |

**来源 PR 不是默认兜底地址**：须先从 PR/任务的明确关联或委派记录确定 canonical task issue；
缺失、多个候选或关系不确定时**不发评论**，保留 `CLAIMED` 并报「canonical task issue 未确认」，
暗号仍引用原 PR。首通道投递结果未知或超时时也不走兜底，避免两条通道重复投递。

兜底评论的形态是**严格受限**的——只含 `role:` 前缀的暗号与 provenance 行：

```
impl: fix PR#53
（watch: relay）
```

**不得**附带解释、总结、建议或任何自由文本。它不是分析，只是把唤醒信号放进持久邮箱，
由人或其他会话转达。评论本身也是投递，所以同样**先认领后写**。

第二行 `（watch: relay）` 是**传输注记**，不是 B.3 的 provenance 标记：`watch` 不在规范的
角色枚举（orch / impl / rev / des / intg）内，该行也不使用 `委派:` 字段。首行是**暗号**而非
输出标记，故不参与 B.3 推导链，也不会被误读为某角色的结论。

**注意这是一次写权限的扩张**：本 skill 对 GitHub 原本只做只读拉取，唯一例外就是这条兜底
评论。这一点已在 skill 硬边界里写明，避免它被当成通用写通道。

## 5. 失效模式与护栏

| 失效模式 | 表现 | 护栏 |
| --- | --- | --- |
| **静默丢包** | 裁定发出但无人被唤醒，无任何告警 | 未分类必上报（§4.4）；健康信号区分三态（§4.5） |
| **重复取件** | 同一评论被两个 watcher 各路由一次 | 单实例锁（§4.1）；先认领后动作（§4.2） |
| **丢失更新** | 并发写状态互相覆盖 | **所有状态写入必须持有同一个锁**（手动运行也一样）；并集合并不是并发写保护 |
| **水位越项** | 投递失败的消息被水位越过，只留在 pending | 水位只推进到已处理/已记账处（§4.3） |
| **重放** | 水位被欠账钉住时，claim 去重记录被裁掉，旧评论重读后重发 | 不截断 `ROUTED`、不删除 `CLAIMED`；本版不做自动 GC |
| **永久阻塞** | 崩溃遗留的锁或 `.mutation` guard 无人能清，watcher 一直跳过 | fail closed 是有意的：简报显式报「锁被占用，必要时人工恢复」，且 `lastCompletedPollAt` 停走使阻塞可见；恢复须人工确认全部运行已停止 |
| **过期取件** | 旧信封在状态已变后被重新读到 | 信封带 exact ref（head/SHA），收件方先核 ref 是否仍是当前 |
| **永久分诊债** | 「已判定不投递」与「投递失败」同为 `CLAIMED`，于是一条已了结的条目每轮都被报成「未完成投递」交人判断 | 终态 `DISMISSED`（§4.2）+ 闭集判据 D1–D5（§4.4）；判据命中不了就落回未分类，不得静默判掉 |
| **权威走私** | 一条看起来像 verdict 但不是权威角色发的评论 | B.3「委派记录先于结论标记」的 provenance 链——这是本总线的**防伪机制**，不是形式主义 |
| **无人在场** | 无人值守运行时需批准的工具调用被停，运行跑不完 | 减少批准需求（allow-list）；健康信号暴露「启动了没推进」 |

## 7. 状态与未决

### 已解决（2026-09-19 复核）

- **无人值守运行跑不完**：候选一被坐实——定时任务的权限模式原本需要一个无人能给的批准。
  改为 `bypass permissions` 后 watcher 立即恢复：状态文件 mtime 更新至 2026-09-19 17:38，
  水位从 `2026-09-16T21:54:10Z` 前进到 `2026-09-19T09:31:30Z`，约 95 条积压被处理。
