# docs/ 文档治理（v0）——提案

> 提案，不是契约。待 Epic Designer 裁定；裁定前不实施。
> 任务 issue：`noos-shuttle#76`。参考模型：中鱼升级项目 Notion 文档治理（经人类指定）。
> **本提案不改变任何既有文档的内容与结构**；它提议的是一套规则，落地另行切片。

## 0. 一句话

**仓库已经自发长出了一套权威声明的实践，而且相当一致；本提案不是要引入它，而是要把它补完、统一形态、
并加上它缺的那一半——「谁是 Current」的正面声明与一个入口。**

## 1. 问题

### 1.1 现状盘点（先看已有的，避免把已解决的问题当问题）

**已经有的**（实证，非推测）：

| 已有实践 | 证据 |
| --- | --- |
| **被取代文档的声明已高度一致** | v0 / v1 / v2 / `reducer-operations-v0` / `n1-n5-amendment-v0` / `m1-m3-amendment-v0` 六份**用同一套措辞**：<br>`> **SUPERSEDED — do not use as current design input.**`<br>`> Current candidate: cross-agent-handoff-escalation-contract-v3.md`<br>+ `frozen at exact commit: <sha>` |
| **被吸收层的 tombstone 清单** | v3 头部：「Supersedes as the current reading path（semantics fully absorbed herein; files retained as provenance tombstones）」+ 四份文件清单 |
| **裁定记录** | `v1-adjudication-record.md` 已经是一份裁定记录：注明裁定来源、结论、「treated as final」、以及 authority baseline 的新 SHA |
| **冻结证据** | `docs/deliberation-harness/evidence/*.json`（4 份），可冻结数值 |
| **提案不得删除** | 规范 §2.1：「proposal 文档一经裁定引用即不得删除；如需清理，先以 commit SHA 引用固化」 |

**共 8 份文档已带这类头部。**

### 1.2 真正缺的四件事

上面那套实践很好，但它是**从「被取代方」写的**。缺的是另一半：

**缺口 1 —— 没有「我是 Current」的正面声明。**
六份文档都指向 v3，但**v3 自己只说 `Status: Consolidated Current Design Contract`**；
`v1-primary-design-current.md` 标题含 "Current"，却**自己声明**「authoritative mechanics remain in the contracts」——
也就是**它不声称自己是 mechanics 的权威**。

结果：**「概念 X 的权威是哪份」仍然必须靠读、靠猜。** 这正是风险 1 的核心。

**缺口 2 —— 没有所有权声明。**
没有任何文档说「我拥有概念 X」。因此当两份文档都声称权威时，**无法机械检出冲突，也无从裁决**。
（Router 解决「先读哪份」，但解决不了「两份打架谁赢」。）

**缺口 3 —— 没有入口。**
`docs/` 下 ~65 份文档（`deliberation-harness/` 约 40 份），**没有 README**。agent 必须已经知道目录结构才找得到东西，
且无法知道自己是否读全了。

**缺口 4 —— 负面知识无落脚点。**
「反设计 / 踩过的坑 / 为什么不采用」**没有任何容器**。旁证：designer 反复在裁定里写
*"Do not reopen PR #57 / Issue #56 Q1–Q6"*——这类信息散落在评论里，靠人记。

**附带缺口 —— 裁定记录不成体系。**
`v1-adjudication-record.md` 证明形态是可行的，但它**没有编号、不可按 ref 引用、不是入口可达的**。
而现行裁定（`PR #58` 评论 `5717715062`、`#56` 评论 `5718137417`）**根本不在仓库里**——
两份相关 proposal 正文对 `PARTIAL_ACCEPT` / `Disposition` / `noos-governor` **命中 0**（三方独立核过）。

### 1.3 本提案的性质：收敛已长出来的东西 + 把 §6 原则下沉一级

规范 **§6** 已确立三层结构，并明令「**平台层与仓库层不得自行演化为第二真源**」——
那是「零竞争权威」原则，**但只覆盖协议层，没有下探到仓库内的文档层**。本提案做的就是把它下推一级。

规范 **§2.3** 已规定裁定记录的形态（交付来源 + 决定性表述原文引用，禁止转述改义）。
所以「裁决登记」**不是新概念，是那份记录的 durable 落点**。

**因此本提案的新增概念被压到最低：**

| 项 | 性质 |
| --- | --- |
| 权威声明头 | **形式化既有实践**（8 份已在写），只补「Current 的正面声明」这一半 |
| 裁决登记 | **形式化既有实践**（`v1-adjudication-record.md` 已是一例）+ 给 §2.3 的要求一个落点 |
| Router | **新增**——但它是索引，不是概念；不带领域结论 |
| 反设计登记 | **新增概念**（唯一一个） |
| 一概念一语义源 | **新增规则**（授权声明的强制力来源） |

## 3. 最小集设计

四项 + 一条冲突消解规则。每项标注**它消除的缺口**。

### 3.1 权威声明头

**消除的缺口**：缺口 1（没有 Current 的正面声明）。

**形态**：沿用既有块引用风格，作为文档开头的固定头：

```markdown
> Authority: Current
> Owns: HandoffPacket, HandoffResult, EscalationPolicy
> Supersedes: cross-agent-handoff-escalation-contract-v2.md@<sha>, ...
```

**取值（四个，冻结）**：

| 值 | 含义 | 作权威读？ | 既有等价写法 |
| --- | --- | --- | --- |
| `Current` | 该概念的权威读取路径 | 是 | 无（**这是要补的那一半**） |
| `Tombstone` | 语义已吸收，仅作追溯 | 否 | `SUPERSEDED — do not use as current design input` |
| `Candidate` | 非权威；须经裁定才晋升 | 否 | — |
| `Frozen` | 可冻结数值/证据，**永不成 Current** | 否 | — |

**明确纪律（承接参考模型）**：**Artifact Type ≠ Authority Level**。
文档名里的 `Final` / `Specification` / `Architecture` / `Consolidated` 只描述**用途与阅读视角**，
**不自动形成权威层级**。权威只来自 `Authority:` 头与 `Owns:` 声明。更详细、更新、挂得更深，都不是覆盖 Current 的理由。

### 3.2 一概念一语义源（规则）

**消除的缺口**：缺口 2（冲突无法检出、无法裁决）。

**规则**：一个概念只有一个语义源，由 `Owns:` 声明。

**为什么它必须与 §3.1 同时存在**：只有头没有 `Owns:`，头就只是一句自我介绍；
只有 `Owns:` 没有头，就不知道谁有权声明。

**可检出性**：同一概念被两份 `Current` 声明 `Owns:` ＝ **可机械检出的冲突**。检出时：

- Router 已指明归属 → 以 Router 指向者为准；
- Router 未列或指向不明 → **视为治理缺陷**，须补 Router，**不得让 agent 自行判断**。

### 3.3 Router

**消除的缺口**：缺口 3（没有入口；无法知道自己读全没有）。

**落点**：`docs/README.md`（`docs/` 目前**没有 README**；单一入口覆盖两个簇：根目录产品文档与 `deliberation-harness/`）。

**形态**：一张「问题 → 读哪份 → 有无下钻 → 停止条件」的表。

**硬规则**：

- **Router 不存领域结论**——只说去哪读，不说结论是什么。
- **链接存在本身不是读取理由**——上层不复制下钻内容，但必须让 agent 知道**自己是否缺了下钻内容**。

### 3.4 裁决登记

**消除的缺口**：附带缺口（裁定不进仓库、不可寻址）。

**性质**：**不是新概念**，是规范 §2.3 所要求的记录的 durable 落点；形态取 `v1-adjudication-record.md` 的蓝本。

**落点**：`docs/rulings/D-YYYYMMDD-NNN.md`，**一裁定一文件**。

**为什么一文件而非单一 `DECISIONS.md`**：

1. 单文件会成为**合并冲突热点**——多会话并发写必撞；
2. 单文件**无法按 exact ref 引用单条裁定**，而规范 §6 要求「裁定与合同类文件始终 SHA 锚定」。
   per-ruling 文件天然可寻址，这才是「入库」的意义。

**条目格式**（照 §2.3 与既有蓝本，不另立）：

```markdown
# D-20260919-001

- 交付来源：<谁、在何处交付>
- Exact target：`<path>@<sha>`
- 来源评论：<link>
- 决定性表述（原文引用，逐字；禁止转述改义）：
  > ...
- 约束对象：<它约束哪份 Current 的哪一段>
- Reopen gate：<什么条件下应重新考虑；无则写「不可重开」>
```

**不可变**：写入后不再编辑；被取代时由新条目 `Supersedes` 指向，旧条目保留。

### 3.5 反设计登记

**消除的缺口**：缺口 4。**这是本提案唯一的新增概念。**

**落点**：`docs/pitfalls/P-YYYYMMDD-NNN.md`，一文件一条——**与裁决登记同构**（两套登记共用一种模式，刻意为之：
少一种概念，也就少一次治理扩张）。

**条目格式**：

```markdown
# P-20260919-001 · <一句话失败签名>

- **失败签名**（症状）：<什么现象说明你正踩这个坑>
- **为什么当时合理**：<当时的选择在当时的约束下为什么是对的>
- **Reopen gate**：<什么条件变化后应重新考虑；无则写「永久排除」>
- **来源**：<评论 / PR / 裁定 link>
```

**收录判据**（引用参考模型的准入测试）：

> 未来一个聪明但不了解今天讨论的人，是否很可能再次问「**为什么不选另一个看起来也合理的方案？**」

答「是」则收录。这也解释了「为什么当时合理」为何必填：**只有这样，未来的人才知道它是永远错误，
还是在旧约束下被淘汰。**

### 3.6 裁定入库的写入路径（人类点名必答）

`rulings/` 若无写入路径就是空中楼阁——**目前没有任何角色被指定把 designer 的裁定固化进仓库**，
这本身就是风险 1 的一个具体成因。逐个回答：

**（1）触发时机与责任人**

不新设角色、不新设职责，而是**搭在既有的合并门禁上**：

> **实施某裁定的 PR，其 body 必须引用该裁定的 `D-` 编号；该编号的条目必须在同一 PR 中创建。**
> 无 `D-` 条目 → 不满足 §1.3 的 PR body 证据要求 → 不得合并。

理由：§1.3 已经要求 PR body 引用 review 证据与被审 head，且 integrator 已经在核这一项。
**把固化挂在这条既有检查上，比新设一个「谁负责归档」的义务可靠得多**——因为门禁是机械的，
而「归档义务」是自愿的。责任人由「谁执行该裁定」自然确定，不需要额外指定。

**兜底（覆盖「裁定存在但无人实施」的情形）**：这正是 `#57`/`#58` 的形态——裁定发出了，
但没有任何实现动作，于是没有 PR 去承载固化。此时由**watcher 上报**（它的「未分类必上报」
已覆盖 designer 原生裁定），由人类或 orchestrator 决定是否立任务。**上报不等于归档，但至少不再静默。**

**（2）源与保真**

以**评论正文为准逐字照录**；规范 §2.3 明文禁止转述改义或代拟 designer 结论。条目必记：

- `source:` 评论 URL + comment id
- `exact target:` 裁定所锚定的 SHA（designer 裁定自带 `Exact target`，如 `5711118315` 锚 `bd3c7af`）
- `provenance:`（如 `des: via connector`）

**（3）在效状态与取代链**

每条自带 `Status: in-force | superseded-by: D-xxx`。**被取代时只标注、不改写正文**（Non-retroactive）。

**注意这条与文档的 `Authority:` 是两个不同的轴**，不要混用：

| 轴 | 取值 | 回答的问题 |
| --- | --- | --- |
| 文档 | `Current` / `Tombstone` / `Candidate` / `Frozen` | 这份**文档**现在算不算权威 |
| 裁定条目 | `in-force` / `pending-incorporation` / `superseded-by: D-xxx` | 这条**裁定**现在还有效吗 |

一条裁定可以「作为事件已成为历史」，而它的**内容**仍活在某个 `Current` 里。
**把这两个轴分开，正是为了避免用「tombstone」去描述一条仍在生效的裁定**（如 `#67` 的裁定至今有效）。

**（4）与 Current 的双向绑定（本提案最关键的一条）**

**裁定记录 ≠ 裁定内容。** 只有记录、没有纳入，就只是「被存档」而不是「被纳入」——
**`#57`/`#58` 正是这个病：裁定存在，但没有任何 Current 反映它。**

因此拓扑是**两条腿**，缺一不可：

```
裁定评论（GitHub，权威源）
   │
   ├─→ 实质内容 ──→ 落到相应 Current（Contract / Domain 文档）…… 这才让裁定「生效」
   │                    └─ 该 Current 反向指回 D-xxx（可追溯）
   └─→ 事件记录 ──→ rulings/D-YYYYMMDD-NNN.md（逐字存档）
```

**硬规则（直接针对 `#57`/`#58` 那个病）**：

> 若一条裁定的内容需要改变某个 `Current` 的语义，则在该 `Current` 更新之前，
> 该条目的 `Status` **必须**标为 `pending-incorporation`，
> 且**不得被当作已生效依据引用**。

这把「已存档但未纳入」从一个**静默的缺口**变成一个**有名字、可检出的状态**。

**（5）与 AGENTS.md / 规范的关系**

规范 **§2.1** 已规定「proposal 文档一经裁定引用即不得删除；如需清理，先以 commit SHA 引用固化」。
裁定登记与之对齐：**退休只能是标注（`Tombstone` / `superseded-by`），不得删除。**

> 勘误：本条要求最初在派单里被引作「`AGENTS.md` §2.3」，实际出处是**规范 §2.1**
> （`AGENTS.md` 无编号小节）。**在一份关于精确引用的提案里，这个出处被引错了**——
> 这本身就是本提案要解决的问题的一个小样本，故如实记录于此。

**（6）谁有权写**

两条路分开，门禁不同：

- **固化裁定（写 `rulings/`）＝ 机械照录**，**不额外加一轮独立复审**。理由是它不产生新语义，
  只是把已在权威源上的内容搬进仓库；加门禁只会拖慢且无安全增量。
- **改 `Current` 段落**按 §1.4 走正常门禁——因为它**产生或改变语义**。

**两者分开的意义**：让「记录」便宜、让「改语义」贵。若把两者绑在一起，就会有人为了省事
而不记录，或为了记录而绕过改语义的门禁。

## 4. 拓扑


```
docs/README.md ………………………… Router（只说去哪读，不存结论）
  │
  ├─→ *-contract-*.md ……………… Current（正面声明 Authority: Current + Owns:）
  │     └─ Supersedes → v0/v1/v2 等 … Tombstone（既有 SUPERSEDED 措辞，grandfathered）
  │
  ├─→ rulings/D-*.md ……………… 裁定逐字存档（§2.3 记录的落点）
  │     └─ 每条 → 指向它所约束的 Current 段落（Reopen gate 记在这里）
  │
  ├─→ pitfalls/P-*.md …………… 反设计登记（失败签名 + 为何曾合理 + Reopen gate）
  │
  ├─→ evidence/*.json …………… Frozen（可冻结数值，永不成 Current）
  │
  └─→ candidates/ …………………… Candidate（显式非权威，须经裁定才晋升）
```

## 5. 阅读预算与下钻提示

```
Router → 1 份 Current →（仅当需要依据时）1 份 ruling/pitfall → Stop
```

**最多 3 篇。** 超出预算通常意味着 Router 写得不清楚，或该问题该被拆开。

**下钻提示契约**：上层不复制下钻内容，但必须让读者知道**自己是否缺了下钻内容**。
「链接存在」不构成读取理由——这条是为了压住「反正都链接了」式的膨胀。

## 6. Non-retroactive（强条）

> **历史文档不追溯服从后来新增的 schema。不得为「格式统一」回写既有文档。**

具体到本仓库（`docs/` 现有 ~65 份 / 12,640 行）：

- **不重写**任何既有文档的内容。
- **Grandfather 条款**：六份已用 `SUPERSEDED — do not use as current design input` 的文档，
  视为已满足 `Authority: Tombstone`，**无需改写**。该旧写法**对新文档关闭**（新文档一律用字段形态）。
- 权威头与登记条目**按需增量**添加：某份文档**下次因实质原因被改动时**，顺手补头。
- Router **一次性编写**覆盖既有集合——它是入口，不写等于没有。
- 唯一允许的批量动作是**加头**（纯增行、不动正文），须独立成 PR，不得混入实质改动。

**为什么是强条**：没有它，本提案读起来像要动 65 个文件；而且「为统一而回写」会污染 git 历史，
恰恰损害本提案要保护的**可追溯性**。

## 7. 晋升与退休

| 从 | 到 | 条件 |
| --- | --- | --- |
| `Candidate` | `Current` | 须引用一份 `D-` 裁定；无裁定则保持 `Candidate` |
| `Current` | `Tombstone` | 被新的 `Current` 完整吸收时；文件**保留**，头改 `Tombstone`，`Supersedes` 反向指回 |
| 任何 | **删除** | 仅限规范 §2.1 允许的路径：先以 commit SHA 固化引用 |

**退休不是删除。** 规范 §2.1 已规定「proposal 文档一经裁定引用即不得删除」；
因此退休的唯一形式是**降级为 `Tombstone` 并说明被谁吸收**——这也正是六份文档已经在做的事。

## 8. 验证用例走查

### 8.1 `#55` §11 的临时降级

**当时**：把 `noos_docs` 两份 Candidate 降级为「受争议引用材料（非 Authority）」，写在 §11 正文里。

**新规则下**：两份 Candidate 在**自己头部**声明 `Authority: Candidate`；`#55` 只需按 Router 引用。
**降级从「事后补救」变成「先验声明」**——这正是缺口 1 要消除的形态。

### 8.2 `#57` / `#58` 裁定只在评论里

**当时**：两份 proposal 正文命中 0；裁定在 `PR #58` 评论 `5717715062` 与 `#56` 评论 `5718137417`。

**新规则下**：落成 `docs/rulings/D-<...>.md`（§2.3 格式，逐字引用），两份 proposal 正文引用该编号。
**附带解决一个已被人类定性的解释问题**：人类确认「design record」指**文档/markdown**而非线程评论；
本提案把这个答案**编码成规则**（§3.4 的落点），而不是留作一次性解释。

### 8.3 v0–v3 版本并存

**当时**：其实**已经解决了一半**——六份文档头部都写了 `SUPERSEDED` 并指向 v3，从任何一份进去都知道它不是权威。

**仍缺的一半**：那个「指向 v3」是**手写的散文**，没有字段；而 **v3 自己没有正面声明 Current**，
也没有任何地方集中列出「有哪些 Current」。所以反过来问「权威是哪份」时，答案不在一处。

**新规则下**：补 `Authority: Current` 正面声明 + Router 集中列出，**两侧都成立**。

### 8.4 本提案自身（自指检验）

本提案是一份 proposal：落地前应为 `Authority: Candidate`，声明 `Owns: DocGovernance`。
若裁定通过，依 §7 **晋升为 `Current`，且必须引用那份裁定的 `D-` 编号**。
**一个不能被自身规则解释的治理提案是不合格的**——这条不过，不得实施。

## 9. 实施切片

> 裁定通过后才拆；此处仅给形状以便评估规模。

1. **Router**：写 `docs/README.md`（一次性覆盖既有集合）
2. **两套登记的模板 + 首批补录**：模板 + 把 `#57` / `#58` 的裁定补录为首批 `D-`（风险 1 的现存缺口）
3. **补 `Current` 正面声明**：先补 v3 等**少数真正的权威文档**（这是缺口 1 的最小动作）
4. **`docs/` 根产品文档按需标注**（增量，不批量）
5. **（可选）可检验性脚本**：检查头是否合法、`Owns:` 是否冲突。**建议先不做**——见 §10 第 1 条

## 10. 未决与风险

1. **过度治理的风险（本提案最大的风险）**。参考模型自带 `Governance Freeze`；本提案已把新增概念压到 **1 个**
   （反设计登记）+ 1 条规则。若裁定过程中再加，应逐条过 §1.3 那道准入门。
   同理 **§9 切片 5 建议先不做**：它会把治理再扩一层，而当前冲突量还不需要机器检。
2. **Router 粒度**未定：单入口是否够，还是 `deliberation-harness/` 需要二级 Router？建议先用单入口，超预算再拆。
3. **覆盖范围**：本提案覆盖 `docs/`。`.noos/` 下文档（handoff、skills）**不在范围**，是否另行处理未定。
4. **「一个概念」的边界**：什么算一个概念需要判断。建议**只在出现实际冲突时**才去界定，
   不预先给概念清单（后者会立刻膨胀）。
5. **Non-retroactive 与「批量加头」的张力**：§6 允许独立成 PR 的批量加头，字面上是「回写」。
   边界是：**加头可，改正文不可**。
6. **Grandfather 条款的代价**：允许两种写法并存（旧散文 / 新字段）意味着校验逻辑要认两种。
   这是为换取 Non-retroactive 付出的代价；若裁定认为统一更重要，可改为一次性改写那六份头部
   （纯增行、内容不变），但那需要显式批准，默认不做。
7. **`Tombstone` vs `Historical` 的用词争议——待人类裁定（占位）**。
   本提案 §3.1 用既有词 `Tombstone`（v3 契约已在用；它也出现在六份文档的现存头部里）。
   已提出的反对理由是「生命周期极性不同」并举 `#67` 裁定至今有效为反例。
   **本提案 §3.6（3）已就此给出解释**：文档权威与裁定在效状态是**两个轴**，`#67` 那类冲突
   属于裁定轴（`in-force`），不该用文档轴的词去描述。因此本提案认为两者可以并存而不冲突。
   **但用词归人类定**；此处留占位，裁定前不据此实施。

## 附录 A：与参考模型的差异（哪些没采纳、为什么）

参考模型列了**八类概念**，本提案**不照搬**，逐条说明：

| 参考模型 | 是否采纳 | 理由 |
| --- | --- | --- |
| Router | **采纳** | 直接对应缺口 3 |
| Semantic Owner（一概念一语义源） | **采纳**（作为规则） | 缺口 2 的正解，Router 不能替代 |
| Historical | **采纳但用既有词** | 用仓库已在用的 `Tombstone`，避免同一概念两个名字 |
| Validation-Frozen | **采纳** | 对应既有 `evidence/` 子目录 |
| Candidate | **采纳** | 对应既有 `candidates/`（原本无晋升规则） |
| Pitfall Registry | **采纳** | 直接对应缺口 4 |
| Project / Domain Current 两级分层 | **未采纳** | 那是为「跨域工作区」设计的。本仓库是单一 git 仓库、单一产品线，不存在跨域状态；采用会直接违反准入门（纯形式完整度） |
| Current Fact Owner | **未采纳** | 其存在理由是「同一数值被多处消费需单一真源」。本仓库当前无此形态；需要时再纳入 |
| Consumer（读但不获重新定义权） | **未采纳** | 那是**权限**概念。本仓库的等价物是既有 review 门禁与 `docs/` 写权限，不必在文档层再造一层 |
| 7 项完整性 × 2+N 知识包 | **未采纳** | 那是**写作标准**，不是**治理结构**。本提案只解决「哪份权威、裁定在哪、负面知识在哪」；写作标准可另行提案 |

## 附录 B：请 Epic Designer 裁定

1. **把规范 §6 的「零竞争权威」下沉到仓库文档层，是否成立？**（本提案的上位依据）
2. **新增的一项概念（反设计登记）与一条规则（一概念一语义源）是否通过准入门？**
   即：它们消除的缺口是否真实且值得。
3. **权威头采纳既有 `SUPERSEDED` 措辞并加 grandfather 条款**（旧写法不再用于新文档、但不回写旧文档），是否认可？
4. **裁决登记用「一裁定一文件」而非单一 `DECISIONS.md`**，是否认可？（理由是 §6 的 SHA 锚定与并发写入）
5. **`Authority:` 的四个取值是否合适？是否需要增删？**
6. **`Consolidated` 这类前缀**（v3 自称 "Consolidated Current Design Contract"）
   是否需要进入取值域，还是只是标题措辞？（按 §3.1 的 `Artifact Type ≠ Authority Level`，倾向后者）
7. **§3.6 的写入路径是否成立？** 特别是最关键的两条：
   （a）把「固化裁定」搭在既有合并门禁上——**实施某裁定的 PR 无 `D-` 条目则不得合并**；
   （b）`pending-incorporation` 这个状态——裁定内容未落进 `Current` 前，**不得被当作已生效依据引用**。
   这两条是直接针对 `#57`/`#58` 那个病设计的：**裁定存在、但没有任何 Current 反映它**。
8. **写权分级是否认可？** 固化裁定＝机械照录、**不加独立复审**；改 `Current` 段落按 §1.4 走门禁。

（见 §10 第 7 条与 §3.6（3）的轴分离解释）。此项不影响其余条款的实施。

裁定后本提案依 §7 晋升为 `Current` 并引用该裁定的 `D-` 编号（§8.4 的自指检验）。
