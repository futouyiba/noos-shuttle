### 1.2 真正缺的四件事

上面那套实践很好，但它是**从「被取代方」写的**。缺的是另一半：

**缺口 1 —— 没有「我是 Current」的正面声明。**

### 1.3 本提案的性质与上位依据

**上位依据（依复审意见改为论证，不再是断言）**

初稿称「规范 §6 已确立零竞争权威原则，只需下沉一级」。**这个转述不准确**，须更正：

- 规范 **§6** 的原文语境是**三层结构**（canonical protocol / 平台 bootstrap / 各仓库 `AGENTS.md`），
  其「平台层与仓库层不得自行演化为第二真源」指的是**相对规范本体**，**不是**「仓库内哪份 docs 是某概念的权威」。
  把它直接读成后者，是**断言而非论证**。

**更准确、也更有力的上位依据是规范 §1.4**——它**已经定义了一个权威文档类别**：

> 触及 **Authority 文件（指各仓库声明为权威基线 / 契约的文档，含本规范自身与 SHA 锚定的契约文件）**
> 的改动，即使位于 `docs/` 下，同样按 1.2 全项，**不得以文档路径降级**；其余纯文档可降级为引用核对。

**即：规范早就承认「权威文件」是一类需要更高审核深度的文档——缺的只是「如何声明自己是那一类」。**
本提案补的正是这个声明形式。§6 的精神（不制造第二真源）作为**类推适用**：

> **§6 的原则在协议层已确立；本提案主张其精神可类推至仓库内的文档层。** 这是本提案的**主张**，
> 需经裁定；未经裁定前不据此实施。

**由此产生的一条自我约束（来自复审 M5）**：

> 本提案中任何**触及规范 §1 / §2 的要求**（例如给 §1.3 加一项 PR body 要求），
> **只能作为「提议」提出，且必须由规范侧落地**。若在仓库层自行增设与规范并行的门禁，
> 那正是本提案所要防止的「第二真源」。§11 集中列出这类提议。

**新增概念计数（依复审 M3 更正为 2）**

初稿把「一概念一语义源」归为「规则」以把新增概念压到 1 个——**复审指出这个归类没有判据，是在回避准入门**。
采纳该意见：**按参考模型的口径，`Semantic Owner` 属于其八类**概念**之一。故本提案的新增概念为 **2 个**

## 3. 最小集设计

### 3.1 权威声明头

**消除的缺口**：缺口 1（没有 Current 的正面声明）。

**一个必须先解决的撞车（来自第一轮 M6 的延伸）**：
`Authority:` **在本仓已被使用**——`implementation-slice-1-submission-ledger-report.md` 第 3 行是
``> Authority: `futouyiba/noos_docs@a49303ca…` (Issue #5 inputs; ...)``，
含义是「本文锚定在哪个权威基线上」，即**来源指针**，**不是层级声明**。

若本提案占用同一字段名，就会让一个已在用的字段产生两种含义。**故本提案改用 `Authority-Level:`**
（`Authority:` 的既有含义保持不变，是否另行规范化为 `Baseline:` 属独立议题，本提案不主张）。

**形态**：

```markdown
> Authority-Level: Current
> Owns: HandoffPacket, HandoffResult, EscalationPolicy
> Supersedes: cross-agent-handoff-escalation-contract-v2.md@<sha>, ...
```

**取值（四个，冻结）**：

| 值 | 含义 | 作权威读？ |
| --- | --- | --- |
| `Current` | 该概念的权威读取路径 | 是 |
| `Historical` | 已退役的权威：仍可读作 provenance，但**不是当前设计输入** | 否 |
| `Candidate` | 非权威；须经裁定才晋升 | 否 |
| `Frozen` | 可冻结数值/证据，**永不成 Current** | 否 |

`Historical` 可保留全文，也可采用 tombstone（最小 provenance 壳）形态；
tombstone **不是第五个 Authority-Level，也不是第二个权威轴**。不引入 `Historical-Complete` 状态。

> **与 §1.4 审核深度的关系（经 designer 裁定）**：**不接受四值与 §1.4 审核深度档的直接等价**。
> designer 原文：「Authority level describes semantic status; review depth is determined by the canonical
> workflow and the nature of the change. A Current/authority change necessarily receives the workflow's
> authority-file treatment, but **the four status values do not themselves redefine §1.4 or create new review classes**.」
> 即：`Current` 变更**必然**获得 §1.4 的 Authority 文件待遇（那是 §1.4 自己说的），
> 但**不能反过来说「某个取值 = 某个审核深度」**。

**`Owns:` 的含义（经 designer 裁定，务必按此读）**：

> **`Owns:` 是「用于冲突检测的语义所有权」，不是排他的文件系统写权限。**

**冲突处置必须是 fail-closed**：

> **两份 `Current` 同时声明重叠的 `Owns:` ＝ 治理冲突，必须 fail closed**——
> **不得**按新旧、文件名、详细度或目录深度来裁决归属。
> （即：不因为某份更新、更详细、名字更"正式"、或挂得更深，就让它赢。）

**纪律（承接参考模型）**：**Artifact Type ≠ Authority Level**。
文档名里的 `Final` / `Specification` / `Architecture` / `Consolidated` 只描述**用途与阅读视角**，
**不自动形成权威层级**。更详细、更新、挂得更深，都不是覆盖 Current 的理由。

### 3.2 一概念一语义源（新增概念 #2）

**消除的缺口**：缺口 2。**准入门**：它消除的是「两份 Current 都声称权威时无从裁决」这一具体失败——
不解决它，缺口 1 补上的声明反而会**制造**冲突（两份都写 `Current` 时局面比现在更糟）。

**规则**：一个概念只有一个语义源，由 `Owns:` 声明。**designer 接受其为不变量**。

**允许投影，禁止重新定义（designer 原文的精确边界）**：

> 派生、解释、消费类文档**可以**重复或投影信息，**但必须指回 owning Current，且不得重新定义它**。
> 这是让 `Owns:` 有用的**最小规则**。

即：**Zero Competing Authority ≠ Zero Duplication**——稳定语义可以少量重复，但**权威只有一个**。

**可检出性**（这一条是它优于一句原则的地方）：同一概念被两份 `Current` 声明 `Owns:` ＝ **可机械检出的冲突**。
检出时：

- **两份 `Current` 声明重叠即 fail closed**，无论 Router 当前指向谁；Router **不能裁决或消解冲突**。
- Router 只导航至相关文档和裁定 provenance；归属须由**显式授权的裁定**解决，再同步文档与索引。
- Router 未列或指向不明也属治理缺陷，**不得让 agent 自行判断**；不得按新旧/文件名/详细度/目录深度裁决。

### 3.3 Router

**消除的缺口**：缺口 3。

**落点**：`docs/README.md`（`docs/` 目前**无 README**；单一入口覆盖两个簇）。

**形态**：「问题 → 读哪份 → 有无下钻 → 停止条件」表；另含**指针、状态、所有权、provenance** 的导航。

**硬规则**（designer 原文的精确边界）：

> Router **可以**是仓库的阅读路由/索引。它必须承载指针 / 状态 / 所有权 / provenance 的**导航**，
> **不得复制实质设计结论**。**它是索引，不是第二个 `Current`。**

配套：**「链接存在」本身不是读取理由**——上层不复制下钻内容，
但必须让 agent 知道**自己是否缺了下钻内容**。

### 3.4 裁决登记

**消除的缺口**：附带缺口（裁定记录**无统一形态、无编号、不可被入口检索**——而非「没有记录」）。

**性质**：给规范 §2.3 的要求一个 durable 落点；形态取 `v1-adjudication-record.md` 的结构 +
**补上该文件缺失的 §2.3 逐字引用字段**。

**落点**：`docs/rulings/D-YYYYMMDD-NNN.md`，**一裁定一文件**。

**为什么一文件而非单一 `DECISIONS.md`**：
（1）单文件是**合并冲突热点**（多会话并发写必撞）；
（2）单文件**无法按 exact ref 引用单条裁定**，而规范 §6 要求「裁定与合同类文件始终 SHA 锚定」。

**条目格式**（照 §2.3）：

```markdown
# D-20260919-001

- Decision: <源裁定的结论>
- Decision status: in-force | superseded-by: <source URL/id；可附 D-xxx>
- Incorporation: pending-incorporation | incorporated | no-current-delta
- 交付来源：<谁、在何处交付>
- Exact target：`<path>@<sha>`
- 来源评论：<URL + comment id>
- Provenance：<如 des: via connector>
- 决定性表述（原文引用，逐字；禁止转述改义）：
  > ...
- 约束对象：<它约束哪份 Current 的哪一段>
- Reopen gate：<什么条件下应重新考虑；无则写「不可重开」>
```

### 3.5 反设计登记（新增概念 #1）

**消除的缺口**：缺口 4（负面知识**有零散实例、无统一归属**——与附带缺口同形）。
**准入门**：它消除的是「同一类坑被重复踩、同一类方案被反复提出并被反复否决」——
注意**不是**「从无到有」（该知识已在多处文档中以不同命名存在，见 §1.2 缺口 4 的举例表），
而是**给已有的零散形态一个可检索的归口**。
判据见下（参考文献的原句），可操作、可判真假。

**收窄后的收录范围（经 designer 裁定）**：

> 一条 `pitfalls/P-*.md` **只有在**满足以下条件时才成立：它是一个**持久的被否决方案 / 已知陷阱**，
> 且**其被重新发现很可能会导致返工或回归**。
>
> **普通的局部 non-goals 留在其所属文档中，不必复制进登记。**

条目须携带：**被否决的命题、理由/证据、权威/provenance、适用范围、重开条件**。

落点：`docs/pitfalls/P-YYYYMMDD-NNN.md`，一文件一条——**与裁决登记同构**（两套登记共用一种模式，刻意为之）。

**条目格式**：

```markdown
# P-20260919-001 · <一句话失败签名>

- **失败签名**（症状）：<什么现象说明你正踩这个坑>
- **为什么当时合理**：<当时的选择在当时的约束下为什么是对的>
- **Reopen gate**：<什么条件变化后应重新考虑；无则写「永久排除」>
- **来源**：<评论 / PR / 裁定 link>
```

**收录判据**（引自参考模型；**其原始出处不在本仓、我也无法直接访问，故按转述引用**）：

> 未来一个聪明但不了解今天讨论的人，是否很可能再次问「**为什么不选另一个看起来也合理的方案？**」

答「是」则收录。「为什么当时合理」必填的理由同原文：**只有这样，未来的人才知道它是永远错误，
还是在旧约束下被淘汰。**

### 3.6 裁定入库的写入路径（人类点名必答）

**（1）触发时机与责任人——本版重写（复审 BLOCKER B1）**

> **初稿错误**：初稿称「实施某裁定的 PR 无 `D-` 条目 → 不满足 §1.3 → 不得合并」，并称「门禁是机械的」。
> **复审指出该推导不成立**：规范 §1.3 只要求「PR 描述引用 **review 证据链接**与被审 **exact head** SHA」，
> 附录 A 的 CI 形态也只是「review 链接 + 7–40 位十六进制 SHA」。
> **一条 `D-` 编号既不是 review 链接也不是 SHA 形态，无法从 §1.3 推导出来。**
> 更要紧的是：若在仓库层自行增设这条门禁，**就是在做本提案所要防止的事**（制造第二真源）。

**修正后的表述（**经 designer 裁定进一步收紧**）**：

> **本提案不主张、也不强制任何「实施 PR 须引用 `D-` 编号」的仓库级要求。**
> 在 canonical workflow spec 明确采纳之前，`noos-shuttle` **不得制造第二套合并策略**。
> 本提案**只提议**该上游变更（见 §11），并**自愿**在自身 PR 中引用 `D-` 编号作为示范；
> 任何对 `noos_docs` 的修改都需要它自己经显式授权的 Work Item。

> **designer 原文（就地记录）**：
> 「Do not claim or enforce "implementation PR must cite a D-number" as repository policy until the canonical
> workflow specification explicitly adopts it. … `noos-shuttle` must not manufacture a second merge policy.」

**在规范侧落地前，责任人按约定确定**：由**执行该裁定的实现方**完成 **Leg A 记录**
（这是归档责任，**无合并门禁故不具强制力**——门禁那一条已 DEFER；但裁定要求两条腿都做才算文档收口，
故它是约定的责任，不是可选项）；
若无人执行该裁定（`#57`/`#58` 正是此形态），则由 **watcher 上报**（其「未分类必上报」已覆盖 designer 原生裁定），
由人类或 orchestrator 决定是否立任务。**上报不等于归档，但至少不再静默。**
该上报规则在**仓库内**只存在于 PR #70 的加固分支（`.claude/skills/noos-watch/SKILL.md` 的「未分类必上报」），
尚未合并；但它在**实际运行的例行任务提示词**里已经生效——机器本地的
`~/.claude/scheduled-tasks/noos-watch/SKILL.md` 把它列为硬边界，并注明「无论 skill 文件是否存在都必须遵守」。
因此本提案在此处的引用**不依赖 #70 合并**；不过该规则**在仓库内不可核验**，引用时应指明上面这个来源。

**（2）源与保真**

以**评论正文逐字照录**；规范 §2.3 禁止转述改义或代拟 designer 结论。必记：`source:`（URL + comment id）、
`exact target:`（裁定锚定的 SHA；designer 裁定自带，如 `5711118315` 锚 `bd3c7af`）、`provenance:`。

**（3）裁定在效、文档收录与取代链**

`Decision status` 记录裁定是否仍在效；`Incorporation` 单独记录文档收录进度。
**`in-force` 与 `pending-incorporation` 可以同时成立**。被取代时保留正文、补记来源裁定的取代指针；
档案中的状态记录不创造、暂停或撤销源裁定的权威。

| 字段 | 取值 | 回答的问题 |
| --- | --- | --- |
| 文档 `Authority-Level` | `Current` / `Historical` / `Candidate` / `Frozen` | 这份**文档**现在算不算权威 |
| 裁定 `Decision status` | `in-force` / `superseded-by` | 这条**裁定**现在还有效吗 |
| 收录 `Incorporation` | `pending-incorporation` / `incorporated` / `no-current-delta` | canonical 文档阅读路径是否已吸收裁定，或不需 Current delta |

一条裁定可以「作为事件已成为历史」，而其**内容**仍活在某个 `Current` 里。
**文档的 `Historical` 不表示其记录的裁定失效；收录待补也不表示裁定失效。**

（例：`#67` 的 disposition 至今有效，宜作 `in-force` 轴的示例；**注**：它是 `PARTIAL_ACCEPT` 且**附 Required delta**，
严格说其要求尚未满足——故它同时是「in-force 但未完成」的样本，不是「已落地」的样本。）

**（4）与 Current 的双向绑定（本版按 designer 裁定**重写**）**

> **初稿错误（本 PR 最重要的一处）**：初稿写「若裁定需改变某 `Current` 的语义，则该 `Current` 更新之前，
> 该条目**不得被当作已生效依据引用**」。**designer 明确否掉了这个语义**：
>
> > 移除任何「有效的 Designer 裁定在 Current 更新前『尚未生效』」的规则。
> > **裁定在其 exact target 上自发布时即具权威**；`pending-incorporation` 只意味着
> > **文档阅读路径尚未吸收它**。
>
> 治理不变量（designer 原文）：
> **LLM proposes; Policy authorizes; Reducer/durable action applies; GitHub records provenance.**
>
> **即：权威来自流程，不来自文档收录。** 收录只让裁定**可被发现**，**不追溯创造它的权威**。
> 初稿把「可发现性」当成了「生效条件」——那会**意外造出第二套权威体系**。

**两条腿（只有一条改变 canonical 阅读路径）**：

```
裁定评论（GitHub，权威源）        ← 权威在此，自发布即生效
   │
   ├─ Leg A：事件/provenance ──→ rulings/D-*.md（逐字存档）
   │        …… 记录裁定「发生过」，不改变任何阅读路径
   └─ Leg B：语义 delta ──────→ 落进 owning Current（当该裁定确实改变它时）
            …… 只有这一步改变 canonical 文档阅读路径；该 Current 反向指回 D-xxx
```

**两条腿都做才算文档收口；但只有 Leg B 改变阅读路径。**
**一条不要求 `Current` 变更的裁定，可以仅凭 provenance/档案收口**——不必为它硬造一次 Current 改动。

**`pending-incorporation` 的正确含义（本版改写）**：

> 它标记的是**文档阅读路径尚未吸收该裁定**，**不是**裁定尚未生效。
> **被要求读 `Current` 的消费者应被告知该 Current 已过期/待补**；
> 但**档案不得抹除或暂停底层裁定**。

**措辞更正（第一轮 m4）**：初稿称这使缺口「可**检出**」。实际上「该裁定是否需要改 Current」
「Current 是否已反映该裁定」都是**语义判断，无机械检出路径**。故降级为：
**有名字、可审计**——它的价值在于让缺口有一个**必须被填写的字段**，而不是让机器发现它。

**档案不是权威（designer 新增的一条）**：

> `D-*` 文件是**权威 GitHub 裁定的 provenance 投影，不是替代权威**。
> 若档案文本与源裁定不一致，**以源裁定为准，且档案算缺陷**。

故条目必须保留：source 评论 URL/id、exact target SHA、decision、以及**逐字决定性文本**
（或一个无歧义的精确引用边界）。

**（5）与既有条款的关系**

规范 **§2.1**（**注意：不是 `AGENTS.md` §2.3——该出处确为规范 §2.1，`AGENTS.md` 无编号小节；
派单中引作出处有误，此项经复审独立确认为正确勘误**）规定被裁定引用的 proposal 不得删除；
如需清理，先以 commit SHA 引用固化。**不据此推导所有文档或登记条目的普遍禁删规则**；
该扩展未获裁定，本轮 defer（§7、§11）。

**（6）谁有权写——本版重写（第一轮 M4）**

> **初稿错误**：初稿称「固化裁定＝机械照录，**不额外加独立复审**」。
> **复审指出这与规范 §1.4 冲突**：§1.4 规定触及 **Authority 文件**的改动「即使位于 `docs/` 下，
> 同样按 1.2 全项，**不得以文档路径降级**」；而 §3.6(4) 自己说条目要写「约束对象：它约束哪份 Current 的哪一段」
> ——即 `rulings/` 是**约束权威文件的文件**。
> 且 §1.5「实现者自身的测试结果不构成独立审核结论」意味着「机械照录」仍需独立核对，
> 以防 §2.3 所禁的**转述改义**。

**修正后的分级**：

| 动作 | 审核深度 |
| --- | --- |
| 固化裁定（新建 `rulings/D-*.md`，纯逐字转录） | 按 §1.4 可降级为**引用核对**——但**仍须一次独立 APPROVE**，核对逐字保真。**此项是本表中唯一的降级主张，已列入 §11 待规范侧确认** |
| 修改 `Current` 段落（产生或改变语义） | **按 1.2 全项**，不得降级 |
| 加 `Authority-Level:` 头（纯增行） | 按 §1.4，触及 Authority 文件 → **走 1.2 全项，不得降级** |

> **第三轮复审指出的更正（⑤）**：本表第 3 行原先写「确需降级须 reviewer/integrator 改判」，**该通道在规范里没有依据**——
> §1.4 规定触及 Authority 文件的改动「**不得以文档路径降级**」，而它的改判句只允许 reviewer/integrator
> **改判升格**，未给降级。且该条降级既未列入 §11，也与 §6 末段、§10 第 5 条的「加头仍需 1.2 全项」冲突。
> **已删除该降级表述**。现本表只剩一处降级主张（**固化裁定那一行**），且已列 §11。
> （刻意写成「固化裁定那一行」而非「第 N 行」——按内容指称不随表格行序变化而失效。）
> ——这与本节自己的主题直接相关：**一份主张「不得自设与规范并行的门禁」的文档，不应同时自设一条规范里没有的降级通道。**

**这条修正本身是本提案应有的样子**：初稿为了让「记录」便宜而擅自降级审核，恰好违反了
**它引用的那条规范**。复审抓住它是对的。

## 4. 拓扑

```
docs/README.md ………………………… Router（只说去哪读，不存结论）
  │
  ├─→ *-contract-*.md ……………… Current（`Authority-Level: Current` + `Owns:`）
  │     └─ Supersedes → v0/v1/v2 等 … Historical（既有 SUPERSEDED / provenance tombstone，grandfathered）
  │
  ├─→ rulings/D-*.md ……………… 裁定逐字存档（§2.3 记录的落点）
  ├─→ pitfalls/P-*.md …………… 反设计登记
  └─→ evidence/*.json …………… Frozen（可冻结数值，永不成 Current）
```

> **`candidates/` 已从拓扑中移除（designer 裁定 REJECT）**：
>
> > Candidate **是语义状态，不是要求的文件系统位置**。既有的或未来的 candidate 目录可以作为
> > **组织上的便利**存在，但**晋升不依赖于把文件移进/移出某个特定目录**。
>
> 这与第一轮的实测一致：**`candidates/` 在两个仓库的默认分支上都不存在**
> （noos_docs 只有 `review-candidate-v1..v4.md` 等**文件**）。既然它从未存在、且晋升不应依赖位置，
> **本提案不再提议新建该目录**——`Candidate` 仅作为 `Authority-Level:` 的一个取值存在。

## 5. 阅读预算与下钻提示

```
Router → 1 份 Current →（仅当需要依据时）1 份 ruling/pitfall → Stop
```

**最多 3 篇。** 超出通常意味着 Router 写得不清楚，或该问题该被拆开。

## 6. Non-retroactive（强条）

> **历史文档不追溯服从后来新增的 schema。不得为「格式统一」回写既有文档。**

- **不重写**任何既有文档的内容。
- **Grandfather 条款**：六份已用 `SUPERSEDED — do not use as current design input` 的文档，
  视为已满足 `Authority-Level: Historical` 的退役语义，既有 `provenance tombstone` 保留形态也无需改写；
  新文档使用 `Historical`，不为采用新名称批量重写旧文档。
- 头与登记条目**按需增量**添加（该文档下次因实质原因被改动时）。
- Router **一次性编写**覆盖既有集合。
- 唯一允许的批量动作是**加头**（纯增行、不动正文），须独立成 PR。**但注意**：按 §1.4，
  加头触及 Authority 文件，仍需 1.2 全项——**「批量」不等于「降级」**。

## 7. 晋升与退休

**总则（designer 裁定）**：

> `Candidate → Current` 与 `Current → Historical` 的转换**需要一次显式授权的裁定与 provenance**；
> **绝不**从合并时间、文件名，或「出现了更新的文档」**推断**。
> **晋升还必须解决重叠的 `Owns:` 声明**（见 §3.1 的 fail-closed）。

| 从 | 到 | 条件 |
| --- | --- | --- |
| `Candidate` | `Current` | 须有**显式授权的裁定** + provenance；且须先消解重叠 `Owns:` |
| `Current` | `Historical` | 被新的 `Current` 完整吸收时——同样须显式授权，不因新文档出现而自动发生；旧文档保留全文或 provenance 壳，头改 `Historical`；新 Current 的 `Supersedes` 指向退役文档，退役文档保留继任者与裁定指针 |

> **范围声明**：规范 §2.1 的不可删除条款只针对**被裁定引用的 proposal 文档**，
> 如需清理，先以 commit SHA 引用固化。推广到所有文档的主张**未获两条源裁定授权，本轮 defer**，
> 不纳入本提案的规则或 §9 实施切片；若重启，须另行明确范围并取得裁定与规范侧授权。
> 上述退役保留要求不等于所有文档永久禁删。

## 8. 验证用例走查

### 8.1 v3 的权威地位靠六份文档「指认」，自己也写了一句但没有字段（**本版替换，第一轮 m5**）

> 初稿用 `noos_docs` 的两份 Candidate 作例——但本提案范围是**本仓库 `docs/`**，
> 而 `docs/README.md` 这个 Router **不可能覆盖另一个仓库**。该用例在自身范围内走不通。

**改用范围内对象**：本仓库的 `cross-agent-handoff-escalation-contract-v3.md` 自称
"Consolidated Current Design Contract"，而**六份文档都指向它**——但那句是**散文而非字段**：
它无法被机械读取，因此入口（Router）也无从据此生成，只能靠人把这句话抄进去。
新规则下它写 `Authority-Level: Current` + `Owns: <契约概念>`，六份指向它的事实就由 Router 集中登记。
