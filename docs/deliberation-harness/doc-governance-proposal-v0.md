### 1.2 真正缺的四件事

上面那套实践很好，但它是**从「被取代方」写的**。缺的是另一半：

**缺口 1 —— 没有「我是 Current」的正面声明。**
六份文档都指向 v3，但 **v3 自己只说 `Status: Consolidated Current Design Contract`**；
`v1-primary-design-current.md` 标题含 "Current"，却自己声明「authoritative mechanics remain in the contracts」——
**它不声称自己是 mechanics 的权威**。

结果：**「概念 X 的权威是哪份」仍然必须靠读、靠猜。**

**缺口 2 —— 没有所有权声明。**
没有任何文档说「我拥有概念 X」。两份文档都声称权威时，**无法机械检出冲突，也无从裁决**。

**缺口 3 —— 没有入口。**
`docs/` 下**不含本文**有 **61 份 `.md` / 12,640 行**，另加 **4 份 JSON 证据**，共 **65 个文件**。
**没有 README。** agent 必须已经知道目录结构才找得到东西，且无法知道自己是否读全了。

> 计数口径（依复审 m1、NIT-1 要求）：以上为**不含本文**的稳定口径——**本文刻意不引用包含自身的行数**，
> 因为任何编辑都会让那个数字立即过期（本项在两轮复审中错了两次，故直接去掉该自指数字）。
> 两点注意：`find docs -type f` 会把 4 份 JSON 计入，故「文件数」与「`.md` 份数」相差 4；
> 全部 65 个文件合计 **23,152 行**（含 JSON），与 `.md` 口径的 12,640 行不可混用。
> 以上三个数字（61 / 65 / 12,640 / 23,152）**均为不含本文的稳定口径**。

**缺口 4 —— 负面知识无落脚点。**

### 1.3 本提案的性质与上位依据

**上位依据（依复审意见改为论证，不再是断言）**

初稿称「规范 §6 已确立零竞争权威原则，只需下沉一级」。**这个转述不准确**，须更正：

- 规范 **§6** 的原文语境是**三层结构**（canonical protocol / 平台 bootstrap / 各仓库 `AGENTS.md`），
  其「平台层与仓库层不得自行演化为第二真源」指的是**相对规范本体**，**不是**「仓库内哪份 docs 是某概念的权威」。
  把它直接读成后者，是**断言而非论证**。

**更准确、也更有力的上位依据是规范 §1.4**——它**已经定义了一个权威文档类别**：

> 触及 **Authority 文件（指各仓库声明为权威基线 / 契约的文档，含本规范自身与 SHA 锚定的契约文件）**
> 的改动，即使位于 `docs/` 下，同样按 1.2 全项，**不得以文档路径降级**；其余纯文档可降级为引用核对。

**即：规范早就承认「权威文件」是一类需要更高审核深度的文档——缺的只是「如何声明自己是那一类」。**
本提案补的正是这个声明形式。§6 的精神（不制造第二真源）作为**类推适用**：

> **§6 的原则在协议层已确立；本提案主张其精神可类推至仓库内的文档层。** 这是本提案的**主张**，
> 需经裁定；未经裁定前不据此实施。

**由此产生的一条自我约束（来自复审 M5）**：

> 本提案中任何**触及规范 §1 / §2 的要求**（例如给 §1.3 加一项 PR body 要求），
> **只能作为「提议」提出，且必须由规范侧落地**。若在仓库层自行增设与规范并行的门禁，
> 那正是本提案所要防止的「第二真源」。§11 集中列出这类提议。

**新增概念计数（依复审 M3 更正为 2）**

初稿把「一概念一语义源」归为「规则」以把新增概念压到 1 个——**复审指出这个归类没有判据，是在回避准入门**。
采纳该意见：**按参考模型的口径，`Semantic Owner` 属于其八类**概念**之一。故本提案的新增概念为 **2 个**
（反设计登记、一概念一语义源），另加 1 项形式化（权威声明头）、1 项索引（Router）、1 项落点（裁决登记）。
两者均在 §3 逐条过准入门。

## 3. 最小集设计

### 3.1 权威声明头

**消除的缺口**：缺口 1（没有 Current 的正面声明）。

**一个必须先解决的撞车（来自复审 M6 的延伸）**：
`Authority:` **在本仓已被使用**——`implementation-slice-1-submission-ledger-report.md` 第 3 行是
`> Authority: \`futouyiba/noos_docs@a49303ca…\` (Issue #5 inputs; ...)`，
含义是「本文锚定在哪个权威基线上」，即**来源指针**，**不是层级声明**。

若本提案占用同一字段名，就会让一个已在用的字段产生两种含义。**故本提案改用 `Authority-Level:`**
（`Authority:` 的既有含义保持不变，是否另行规范化为 `Baseline:` 属独立议题，本提案不主张）。

**形态**：

```markdown
> Authority-Level: Current
> Owns: HandoffPacket, HandoffResult, EscalationPolicy
> Supersedes: cross-agent-handoff-escalation-contract-v2.md@<sha>, ...
```

**取值（四个，冻结）**：

| 值 | 含义 | 作权威读？ | 与 §1.4 的关系 |
| --- | --- | --- | --- |
| `Current` | 该概念的权威读取路径 | 是 | **属 §1.4 的「Authority 文件」→ 改动走 1.2 全项** |
| `Tombstone` | 语义已吸收，仅作追溯 | 否 | 仍属契约文件 → 同样走 1.2 全项 |
| `Candidate` | 非权威；须经裁定才晋升 | 否 | 提案类，按 §1.4 该档判定 |
| `Frozen` | 可冻结数值/证据，**永不成 Current** | 否 | 证据，非契约 |

（**待裁定**：四个值是否应直接映射为 §1.4 的审核深度档？见附录 B 第 5 问。）

**纪律（承接参考模型）**：**Artifact Type ≠ Authority Level**。
文档名里的 `Final` / `Specification` / `Architecture` / `Consolidated` 只描述**用途与阅读视角**，
**不自动形成权威层级**。更详细、更新、挂得更深，都不是覆盖 Current 的理由。

### 3.2 一概念一语义源（新增概念 #2）

**消除的缺口**：缺口 2。**准入门**：它消除的是「两份 Current 都声称权威时无从裁决」这一具体失败——
不解决它，缺口 1 补上的声明反而会**制造**冲突（两份都写 `Current` 时局面比现在更糟）。

**规则**：一个概念只有一个语义源，由 `Owns:` 声明。

**可检出性**（这一条是它优于一句原则的地方）：同一概念被两份 `Current` 声明 `Owns:` ＝ **可机械检出的冲突**。
检出时：

- Router 已指明归属 → 以 Router 指向者为准；
- Router 未列或指向不明 → **视为治理缺陷**，须补 Router，**不得让 agent 自行判断**。

### 3.3 Router

**消除的缺口**：缺口 3。

**落点**：`docs/README.md`（`docs/` 目前**无 README**；单一入口覆盖两个簇）。

**形态**：「问题 → 读哪份 → 有无下钻 → 停止条件」表。

**硬规则**：Router **不存领域结论**；**「链接存在」本身不是读取理由**——上层不复制下钻内容，
但必须让 agent 知道**自己是否缺了下钻内容**。

### 3.4 裁决登记

**消除的缺口**：附带缺口（裁定记录**无统一形态、无编号、不可被入口检索**——而非「没有记录」）。

**性质**：给规范 §2.3 的要求一个 durable 落点；形态取 `v1-adjudication-record.md` 的结构 +
**补上该文件缺失的 §2.3 逐字引用字段**。

**落点**：`docs/rulings/D-YYYYMMDD-NNN.md`，**一裁定一文件**。

**为什么一文件而非单一 `DECISIONS.md`**：
（1）单文件是**合并冲突热点**（多会话并发写必撞）；
（2）单文件**无法按 exact ref 引用单条裁定**，而规范 §6 要求「裁定与合同类文件始终 SHA 锚定」。

**条目格式**（照 §2.3）：

```markdown
# D-20260919-001

- Status: in-force | pending-incorporation | superseded-by: D-xxx
- 交付来源：<谁、在何处交付>
- Exact target：`<path>@<sha>`
- 来源评论：<link>
- Provenance：<如 des: via connector>
- 决定性表述（原文引用，逐字；禁止转述改义）：
  > ...
- 约束对象：<它约束哪份 Current 的哪一段>
- Reopen gate：<什么条件下应重新考虑；无则写「不可重开」>
```

### 3.5 反设计登记（新增概念 #1）

**消除的缺口**：缺口 4。
**准入门**：它消除的是「同一类坑被重复踩、同一类方案被反复提出并被反复否决」——
判据见下（参考文献的原句），可操作、可判真假。

**落点**：`docs/pitfalls/P-YYYYMMDD-NNN.md`，一文件一条——**与裁决登记同构**（两套登记共用一种模式，刻意为之）。

**条目格式**：

```markdown
# P-20260919-001 · <一句话失败签名>

- **失败签名**（症状）：<什么现象说明你正踩这个坑>
- **为什么当时合理**：<当时的选择在当时的约束下为什么是对的>
- **Reopen gate**：<什么条件变化后应重新考虑；无则写「永久排除」>
- **来源**：<评论 / PR / 裁定 link>
```

**收录判据**（引自参考模型；**其原始出处不在本仓、我也无法直接访问，故按转述引用**）：

> 未来一个聪明但不了解今天讨论的人，是否很可能再次问「**为什么不选另一个看起来也合理的方案？**」

答「是」则收录。「为什么当时合理」必填的理由同原文：**只有这样，未来的人才知道它是永远错误，
还是在旧约束下被淘汰。**

### 3.6 裁定入库的写入路径（人类点名必答）

**（1）触发时机与责任人——本版重写（复审 BLOCKER B1）**

> **初稿错误**：初稿称「实施某裁定的 PR 无 `D-` 条目 → 不满足 §1.3 → 不得合并」，并称「门禁是机械的」。
> **复审指出该推导不成立**：规范 §1.3 只要求「PR 描述引用 **review 证据链接**与被审 **exact head** SHA」，
> 附录 A 的 CI 形态也只是「review 链接 + 7–40 位十六进制 SHA」。
> **一条 `D-` 编号既不是 review 链接也不是 SHA 形态，无法从 §1.3 推导出来。**
> 更要紧的是：若在仓库层自行增设这条门禁，**就是在做本提案所要防止的事**（制造第二真源）。

**修正后的表述**：

> **本提案提议给规范 §1.3 增加一项 PR body 要求**——实施某裁定的 PR，其 body 须引用该裁定的 `D-` 编号。
> **该修改属规范级，须按规范第 1 节走独立审核后由规范侧落地**（见 §11）。**在规范侧落地之前，
> 本项不具备强制力**，`rulings/` 的写入依赖下述责任约定。

**在规范侧落地前，责任人按约定确定**：由**执行该裁定的实现方**在其实施 PR 中固化；
若无人执行该裁定（`#57`/`#58` 正是此形态），则由 **watcher 上报**（其「未分类必上报」已覆盖 designer 原生裁定），
由人类或 orchestrator 决定是否立任务。**上报不等于归档，但至少不再静默。**

**（2）源与保真**

以**评论正文逐字照录**；规范 §2.3 禁止转述改义或代拟 designer 结论。必记：`source:`（URL + comment id）、
`exact target:`（裁定锚定的 SHA；designer 裁定自带，如 `5711118315` 锚 `bd3c7af`）、`provenance:`。

**（3）在效状态与取代链**

`Status: in-force | pending-incorporation | superseded-by: D-xxx`。**被取代时只标注、不改写正文**。

**与文档 `Authority-Level:` 是两个不同的轴**，不可混用：

| 轴 | 取值 | 回答的问题 |
| --- | --- | --- |
| 文档 | `Current` / `Tombstone` / `Candidate` / `Frozen` | 这份**文档**现在算不算权威 |
| 裁定条目 | `in-force` / `pending-incorporation` / `superseded-by` | 这条**裁定**现在还有效吗 |

一条裁定可以「作为事件已成为历史」，而其**内容**仍活在某个 `Current` 里。
**分开两个轴，正是为了避免用 `Tombstone` 去描述一条仍在生效的裁定。**

（例：`#67` 的 disposition 至今有效，宜作 `in-force` 轴的示例；**注**：它是 `PARTIAL_ACCEPT` 且**附 Required delta**，
严格说其要求尚未满足——故它同时是「in-force 但未完成」的样本，不是「已落地」的样本。）

**（4）与 Current 的双向绑定（最关键的一条）**

**裁定记录 ≠ 裁定内容。** 只有记录、没有纳入，就只是「被存档」而不是「被纳入」。

```
裁定评论（GitHub，权威源）
   │
   ├─→ 实质内容 ──→ 落到相应 Current …… 这才让裁定「生效」
   │                    └─ 该 Current 反向指回 D-xxx（可追溯）
   └─→ 事件记录 ──→ rulings/D-YYYYMMDD-NNN.md（逐字存档）
```

**硬规则**：

> 若一条裁定的内容需要改变某个 `Current` 的语义，则在该 `Current` 更新之前，
> 该条目的 `Status` **必须**标为 `pending-incorporation`，且**不得被当作已生效依据引用**。

**措辞更正（复审 MINOR-4）**：初稿称这使缺口「可**检出**」。实际上「该裁定是否需要改 Current」
「Current 是否已反映该裁定」都是**语义判断，无机械检出路径**。故降级为：
**有名字、可审计**——它的价值在于让缺口有一个**必须被填写的字段**，而不是让机器发现它。

**（5）与既有条款的关系**

规范 **§2.1**（**注意：不是 `AGENTS.md` §2.3——该出处确为规范 §2.1，`AGENTS.md` 无编号小节；
派单中引作出处有误，此项经复审独立确认为正确勘误**）规定 proposal 不得删除。裁决登记与之对齐：
退休只能是标注，不得删除。

**（6）谁有权写——本版重写（复审 MAJOR M4）**

> **初稿错误**：初稿称「固化裁定＝机械照录，**不额外加独立复审**」。
> **复审指出这与规范 §1.4 冲突**：§1.4 规定触及 **Authority 文件**的改动「即使位于 `docs/` 下，
> 同样按 1.2 全项，**不得以文档路径降级**」；而 §3.6(4) 自己说条目要写「约束对象：它约束哪份 Current 的哪一段」
> ——即 `rulings/` 是**约束权威文件的文件**。
> 且 §1.5「实现者自身的测试结果不构成独立审核结论」意味着「机械照录」仍需独立核对，
> 以防 §2.3 所禁的**转述改义**。

**修正后的分级**：

| 动作 | 审核深度 |
| --- | --- |
| 固化裁定（新建 `rulings/D-*.md`，纯逐字转录） | 按 §1.4 可降级为**引用核对**——但**仍须一次独立 APPROVE**，核对逐字保真 |
| 修改 `Current` 段落（产生或改变语义） | **按 1.2 全项**，不得降级 |
| 加 `Authority-Level:` 头（纯增行） | 按 §1.4，触及 Authority 文件 → 走 1.2 全项；确需降级须 reviewer/integrator 改判 |

**这条修正本身是本提案应有的样子**：初稿为了让「记录」便宜而擅自降级审核，恰好违反了
**它引用的那条规范**。复审抓住它是对的。

## 6. Non-retroactive（强条）

> **历史文档不追溯服从后来新增的 schema。不得为「格式统一」回写既有文档。**

- **不重写**任何既有文档的内容。
- **Grandfather 条款**：六份已用 `SUPERSEDED — do not use as current design input` 的文档，
  视为已满足 `Authority-Level: Tombstone`，**无需改写**；该旧写法**对新文档关闭**。
- 头与登记条目**按需增量**添加（该文档下次因实质原因被改动时）。
- Router **一次性编写**覆盖既有集合。
- 唯一允许的批量动作是**加头**（纯增行、不动正文），须独立成 PR。**但注意**：按 §1.4，
  加头触及 Authority 文件，仍需 1.2 全项——**「批量」不等于「降级」**。
