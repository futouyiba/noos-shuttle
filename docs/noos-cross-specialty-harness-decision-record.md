## 1. 确认与修订依据

以下来源均为本产品设计对话。短答确认保留其所指问题，避免脱离语境扩大含义。

### D1 — 产品定位与专业分工（用户确认）

关键原文：

> “Coding 内部的 Harness 他们自己管。”
>
> “Design 内部的 Harness 由于发生在 ChatGPT 这种 chatbot 里面，我们就来接管。”
>
> “或者准确地来说，是 Noos Hub 来接管。Noos Shuttle 是浏览器当中跟 Chatbot 和画图工具桥接的一个桥梁，一个交互界面。”

角色隔离原文：

> “搞设计的，就专门搞设计，搞开发的就专门搞开发，让他们的上下文维持相对隔离”

理由：用户希望保留偏好的深度讨论体验，同时减少跨工具搬运。由此收敛到跨专业工作连续性，而不是让某个工具替代全部专业能力。关于模型聚焦的动机不作为未经验证的性能结论。

### D2 — 自动往返与触发（用户确认）

真实痛点原文：

> “需要我来回传话。这里就涉及到，怎么能自动触发，怎么能顺畅传递”

用户以批注“是啊”确认的问题：

> “你是否希望指定好设计角色后，开发请求能直接触发它思考并答复，不再逐次等你点击？涉及超出授权的决定，再停下来找你。”

确认的是授权范围内免逐次点击，不是批准任意评论触发执行、某种适配器方案或解除自动恢复门禁。

### D3 — 不抢占主讨论（用户确认）

用户“赞同”的建议原文：

> “先排队、不抢占当前讨论，在安全的时机自动处理；不要默认另开一个缺少设计背景的‘临时设计师’。”

确认未定义“安全时机”。后续提出有界工作会话只是可选扩展，尚未取代此方向。

后续 D7 转向按输入排队的体验探索；本条不再被解释为整段人类讨论期间必须禁止外部请求，原确认来源保留不变。

### D4 — 默认手动忙闲开关（助手撤回）

助手曾提出“正在与我讨论 / 可自动接单”模式，用户追问：

> “这样操作会不会很繁琐？容易忘？”

助手撤回把手动切换作为默认入口的建议。理由：容易把人工传话变成人工维护开关；忘记切换可造成积压或突然插话。用户没有因此批准任何替代架构。

### D5 — 有界委派与工作会话分类（候选，未确认）

分析逐步区分了材料不足、未沉淀判断与没有裁决权；提出在自然工作交付点明确范围，并以交付物区分调研、设计、验证、评审和沉淀。

用户询问会话种类及谁回应 Coding Agent，是进一步了解，不是批准新角色或委派。当前候选细节只维护在产品设计稿，不在此复制第二份。

### D6 — 按主题组织设计对话（用户使用事实）

助手曾询问委派单位是“一个功能”还是“一轮开发任务”。用户纠正这个二选一，说明实际习惯：

> “我大部分情况下对chatgpt会分主题来问，来讨论，来驱动。比如中鱼整体设计、中鱼烘焙整体设计、中鱼响应模块整体设计、其中的饵和姿态的吸引因子拆分和聚合设计，都会是单独对话。互相之间使用文档来互通信息”

据此区分主题负责人与有界请求，撤回以每个功能 / 实现任务组织负责会话的默认建议。功能或任务仍可限定一次交付的范围，但不能据此决定主题会话的寿命；不同主题也不自动取得上下级裁决关系。

用户同时重提“如果我正在和这个负责人聊呢”，说明另外创建工作会话并未解决同一主题中人与自动请求相遇的问题。当时助手提出离开后自动处理的候选，未经用户确认；该候选随后被 D7 的输入排队方向取代，不由本条使用事实推导为已批准。

### D7 — 从判断忙闲转向输入排队（用户建议，细节待定）

用户以自己的 Agent 使用体验提出：

> “有其它agent跟一个对话任务agent说话，它就响应。我新敲一条指令，就接在后面，现在看起来也没出什么大问题。”
>
> “所以先解决让人敲的时候‘排队’这个chatbot没有的体验，是不是就好了很多？”

据此优先探索让用户在生成期间仍能编辑、提交待发输入，并让人与 Agent 的请求先后处理。助手撤回将“用户离开主题”作为默认处理前提的候选：此前把保护单次处理扩大成保护整段讨论，增加了忙闲判断和返回冲突的复杂性。

用户的体验描述不是对各产品现有队列能力的核验，也未决定严格先后顺序、优先级或输入框形态。产品稿暂以依序处理为最小候选，保留排队与明确中断的区别；话题交错的可接受程度、平台可行性与权限映射仍待验证，不视为契约批准。

### D8 — 上下文保护与回应来源单列（用户提出的范围区分）

用户补充：

> “离开才回应，这种设计可以是单独的东西，例如人可以显式地锁住一个对话，不让它徒增上下文。”
>
> “例如是不是fork一个对话作为回应源，那些是另外一个主题。”

因此区分三件事：输入如何排队、主对话是否允许外部上下文进入、外部问题由什么承载回应。D7 撤回的是把离开作为默认接单前提，不是永久排除可选的对话保护策略。用户没有批准具体锁定行为、fork 架构或自动解除条件。

这些独立议题登记到当前稿 Q11 / Q12，不把新方案塞入输入排队的当前讨论。用户同时询问是否使用 Issues 跟踪开放事项；这是工作方式讨论，尚非创建远端 Issue 或启动新任务的授权。

## 2. 输入材料：裁决请求 / 结果候选

来源：用户以“看看这种情况”提供《已粘贴的文本.txt》，开头为“继续收敛的话，我建议先把协议钉死”。这是候选方案，不是运行事件日志或本任务的执行指令。

核心目标原文：

> “让 CC 在遇到 Authority Boundary 时，可以自己把问题送到 GitHub；裁决方只需要读取 GitHub；CC 再自己把裁决结果取回来。”

材料提出：单一问题和 exact target；GitHub 持久 Request / Result；证据引用；裁决给出允许、不允许和 required actions；结果返回原任务。它暂留人工“看裁决队列”触发，用户随后明确希望免除这一负担。

采用前的待核对点，而非正式 review findings：

- Result 自称 `RESOLVED` 不等于现有 Escalation 已经通过授权 reducer 完成 resolution。
- `authority sufficient` 与 `target_sha compatible` 尚需明确判断规则，字段名称不能保证确定性。
- §6 允许证明兼容后消费，末尾又建议 v0 不自动判断兼容，存在需统一的候选口径。
- “不做 Governor”不消除授权归属问题，也不允许另造平行生命周期。

## 3. 四个历史请求的过程推演

读取版本：本仓库 `374a2feb4d08e60ac459d352ff320c39d4df82b5`。
交叉来源：[人工协作基线 Trace A / B](deliberation-harness/cross-agent-handoff-manual-dogfood-baseline-v0.md)。

原提案保留的“待裁定”不是今天仍未解决的证据。本轮不重新裁定或复审历史议题，也不将历史平台限制视为当前事实。下列可准备工作是反事实产品推演，不是自动化效果测量。

| 历史请求 | 来源事实 | 可准备的材料 | 不可绕过的边界 |
| --- | --- | --- | --- |
| [结果回传账本](deliberation-harness/v1-design-proposal-result-delivery-lane.md) | 存在两种解释；Trace A 记载部分疑问源于过时依据，后续明确复用 SubmissionOperation | 文档版本、身份和回执对照、相关裁决原文 | 找到较新文档不等于工作自动采用新基线 |
| [Reducer 定位](deliberation-harness/v1-design-proposal-reducer-model.md) | 从缺少实现机制推断职责可能不同；Trace A 记载设计方未接受此重定义 | 契约要求、代码现状、缺口证据 | 缺实现不是更改架构职责的授权 |
| [W11 执行身份](deliberation-harness/w11-settle-hop-design.md) | 提案包含 A/B/C，文末记录了裁定后的进一步收窄 | 编号来源、冲突路径、影响及方案代价 | 谁产生权威执行身份是结构决定，不能按名称相近自动回答 |
| [FORKED 能力缺口](deliberation-harness/v1-design-proposal-fork-adapter-gap.md) | 提案混合能力事实和语义调整；Trace B 后续区分创建来源与上下文保真度 | 指定版本能力、验证证据、替代方式及保真损失 | “做不到”不能直接推导“可以改要求” |

推论：

- 一条请求常混合材料准备和待裁决部分，不宜整条硬分为“查资料”或“需要设计”。
- 代码取证优先留给原 Coding Agent，避免 Hub 为每条问题新增助手。
- 现有裁决可减少重复讨论，但不因内容相似自动解除当前 blocker。
- 这些定向升级案例不能用于估算自动答复率；它们没有证明主会话安全处理时机已经解决。

## 4. 自动处理方案的取舍

| 方案 | 收益 | 代价或反例 | 当前态度 |
| --- | --- | --- | --- |
| 人工忙闲模式 | 投递许可直观 | 用户易忘切换，变成每日操作负担 | 已撤回作为默认入口的建议 |
| 无操作后自动输入 | 不需要设置模式 | 阅读、思考或看其他资料也会无输入 | 不以此单独证明安全或授权 |
| 全部等待主会话 | 背景完整、职责集中 | 队头阻塞，可能一直等不到时机 | 无委派时保留，但需可见恢复路径 |
| 每条请求复制全权设计师 | 便于并行 | 理由丢失、权限分叉、重复成本 | 不建议作为默认 |
| 原 Agent 准备 + 指定角色裁决 | 减少取材与传话 | 没有直接解决主会话忙碌问题 | 当前最小闭环候选 |
| 明确有界工作会话 | 可避开主讨论抢占 | 材料、授权、结果接纳及并行能力需验证 | 可选扩展，未确认 |

问题的核心不是页面是否空闲，而是注意力、材料充分性与权限是否允许处理。普通单会话缺少可靠调度能力时，不能同时承诺原会话独占、立即处理、绝不打断和完全无需交接意图。

有界委派将重复传话的成本转为工作交付时的材料与职责准备；只有总负担实际下降才值得采用。可并行不等于更省 token 或时间，不据此先建通用团队编制或复杂 Governor。

## 5. 压力案例与证据边界

### 主讨论探索“取消登录”，开发仍问旧登录方案

- 未确认想法不能静默成为新执行依据。
- 工作侧声明使用的授权版本；需要暂停相关实施时应形成明确范围变化，不能让 Hub 从语气猜测。
- 依据经授权变更后，在途旧结果需重新核对，不以消息新旧顺序自动采纳。

这是反事实推演，不要求实现自然语言 topic overlap 或 compatibility 裁判。

### 原设计会话更换，外部请求尚未结束

工作记忆可以解释理由，但待办还需要原任务、负责角色和返回地址的持久关联。单纯保存摘要不足以证明请求已交接。

### 用户停顿、目标离线或后台能力不足

无输入不等于可以插话。GitHub 有记录不等于目标已唤醒；Hub 不可用不应丢失共享来源。没有安全处理通道时，应保留请求并显示阻塞，不将原型假设写成已实现保证。

工作记忆不能保证复制原会话全部判断能力，更不意味着导出模型隐藏推理。缺少相关理由时要补充或升级，不以全量历史自动代替。
