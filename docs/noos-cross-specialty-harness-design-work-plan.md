## 1. 持续工作约定

用户原文：

> “我一边讨论，你一边把一些点就往设计文档里面去改。然后改着改着达到了一个相对稳定的程度就形成提交，防止聊着聊着把前面的东西又忘了。”

文档卫生要求原文：

> “不同种类的文档要分开。例如负责设计稿的，负责历史记录的，等等。”

进一步约定：尽可能支持渐进式读取、修改与写入；不因开始一轮讨论就重读、重写整套文档。

执行方式：

- 每轮聚焦一个主题，及时整理共识、候选和未决项，不等整段讨论结束才沉淀。
- 确认必须有实际来源；用户询问、要求继续或批准讨论计划，不等于接受全部建议。
- 文档承接跨会话记忆，不声称聊天平台已保存永久 memory；不默认重放整个对话。
- 稳定的一组内容可做本地检查点提交；提交次数不等于阶段完成数，候选检查点不等于 APPROVE。
- 不自动 push、创建远端 PR、合并、部署、关闭任务或进入产品实现。需要时按授权和[仓库协作规范](https://github.com/futouyiba/noos_docs/blob/main/docs/agent-workflow.md)执行。
- 稳定设计接受独立评审；触及权威契约的差异另行裁定，不自我批准。

本次范围更新：用户明确要求快速设计裁决整体流程并交给 CC 开发，故允许本任务准备、投递有界开发交接及必要的只读辅助调查；本会话继续承担 Designer，不替 CC 编写产品实现。没有因此取得 push、merge、部署、关单或放开恢复门禁的授权。

## 2. 文档分工与维护规则

| 文档 | 只负责什么 | 不放什么 |
| --- | --- | --- |
| 当前产品设计 | 现行方向、候选方案、职责、场景、未决问题与验收关注点 | 聊天流水、被撤回方案全文、每轮提交说明 |
| 决策依据与历史 | 必要原文、决定和修订理由、重要替代方案、案例证据、版本锚点 | 复制一份完整当前设计，或把每次“继续”记成事件 |
| 本工作计划 | 协作约定、阶段状态、下一讨论入口与交付门禁 | 产品细节和设计结论的第二份真源 |

更新时遵循：

1. 修改对应主题的既有段落，不在文末不断追加“又一轮分析”。
2. 已解决问题从当前待决清单移出；保留必要的决定依据，而非让新旧结论并排都像有效。
3. 被取代的方案在历史中标明状态和原因，当前设计只保留有效表述。
4. 同一事实只维护一处正文，其余用链接；历史不能覆盖当前规范。
5. 文件按职责拆分，不按聊天轮次或每个小观点建文件；不提前拆出空白 schema、接口或独立章节文档。
6. 使用稳定标题和标识作导航，不以易漂移的行号作持久索引；更名或迁移时修复入链。Git 保存逐行历史，文档只记录有意义的设计变化。
7. 整理只改变表达与位置，不借机改变确认状态、授权范围或既有契约。

### 2.1 渐进式读取、修改与写入

**读取：入口 → 主题 → 必要依赖。** 先看文件职责、状态及目录，用标题或问题标识定位相关章节。需要确认理由、来源或处理冲突时再展开对应历史和证据，不默认扫描全部历史、Vault 或其他主题。影响授权或契约时，必须读足适用条款与依赖；渐进式不等于省略关键限制。

**修改：局部正文 → 关联检查。** 编辑前先读目标段落、父级状态说明和必要上下文，再对当前主题做局部 patch。确认候选或解决问题时检查关联的状态、未决项及引用，不只在尾部追加一句造成前后矛盾。除必要整理外不整篇重写，不顺手改无关章节。

**写入：按内容性质及时落盘。** 共识与方案写到设计稿的所属主题；实质性取舍及来源写入决策记录；进度或工作方式写入本计划。每轮只改受影响的文件，不要求三份一起更新。未定内容保留候选状态，不等所有问题解决才写，也不为每次短答建立历史条目。

章节尽量自包含：表达当前状态、内容、边界与必要依赖，避免读者必须追完整聊天才理解。只有主题已可独立维护、引用负担或规模确实增长时才拆子文档，并在原入口留下简短指针；不按轮次或为了缩短文件机械拆分。

局部更新后检查受影响的链接、锚点、确认状态和 diff。主题跨越多个职责、发生契约变化或准备阶段交付时，扩大为一致性检查；仅导航/结构检查不能代替语义评审。相对稳定后提交检查点，不把每次写入强制变成提交。

### 2.2 开放事项的跟踪（候选）

建议采用“设计稿保存内容，Issue 跟踪工作”的分工，不把每个念头都建成任务：

对 NOOS 本身的产品设计工作，建议默认使用 `futouyiba/noos-shuttle` 的 GitHub Issues 承接独立设计议题，不另建一套待办系统。它是本项目的工作跟踪选择，不等于确认产品必须以 GitHub 作为运行时中转，也不关闭产品稿 Q10。设计正文继续留在文档；这一工具选择仍是建议，不将用户询问理解为创建远端议题的授权。

- 当前主题内、预计近期可收敛的小问题留在设计稿的 Q 清单；需要跨轮挂起、独立讨论、分派或影响里程碑的议题，才考虑建立设计 Issue。
- 创建前查询已有 Issue，优先关联同一问题，不重复建单。Issue 以问题命名，不把候选解法写成已经决定的实现任务。最小内容是用户场景、尚需裁定的问题、范围与非目标、当前设计入口及收敛条件；没有落实负责人或优先级时如实留待安排。
- 设计稿维护当前方案和边界；决策记录维护理由与否决依据；Issue 维护负责人、推进状态、依赖与讨论入口。进入 Issue 跟踪后，Q 清单只保留问题及指针，不再复制一份进度账本。
- 以链接连接，不复制长篇聊天或整份设计稿。共享引用必须可访问且标明适用版本；未发布的本地候选不能伪装成对方可读的已批准规范。
- 每次阶段收敛时检查相关开放项：继续保留、另开设计讨论、已裁定或明确不做，并把结论归回设计稿或决策记录。Issue 不以“已经实现”作为所有设计议题的唯一结束方式；外部状态变更仍按授权执行。

当前可提升的两个议题是“主题对话的上下文保护与接单策略”（Q11）和“外部请求的回应来源与主对话关系”（Q12）。先作为本地候选入口保留；不在本轮创建远端 Issue，也不默认选择 fork。完整跟踪约定尚待用户确认。

## 3. 四阶段推进

| 阶段 | 状态 | 目标与退出条件 |
| --- | --- | --- |
| 1. 定位与边界 | 已沉淀，未独立评审 | 记录用户共识、职责边界、既有依据和开放问题 |
| 2. 真实场景与优先级 | 进行中 | 补齐三个场景的实际旅程，经用户确认后明确首版必需能力、优先级与后续扩展 |
| 3. 工作记忆与协作规则 | 提前探索，未完成 | 明确信息层次、角色职责、对象对应及需要裁定的差异 |
| 4. 交互与首个切片 | 提前探索，未选定切片 | 已有 B1 输入排队草图；仍需选择优先场景、验证体验与恢复路径并明确实现边界，之后才讨论实现授权 |

第二阶段三个场景：

- A：长期设计讨论沉淀后，换新对话继续。尚需实际迁移经历、丢失内容与重述成本。
- B：设计与开发或视觉角色之间交付并回传。目前深入 B1：开发遇到设计边界、用户来回传话。
- C：调研、设计、视觉探索、原型实现与验证反复迭代。尚需完整真实工作案例。

每个场景补齐用户目标、分工、必要上下文、交付、人工决定点、完成标准和失败恢复；不代填为已经验证的事实。

## 5. 验证与交付

文档修改检查本地链接、空白错误、状态一致性和变更范围；不运行与纯文档整理无关的构建。作者检查不是独立 review。

产品验收问题维护在当前设计稿，不在此重复。真实场景验证尚未执行，案例分析不能证明收益或平台能力。进入实现或集成前按相应流程重新检查证据与授权。
